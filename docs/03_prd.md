# PRD（改訂版）

## 1. 文書の目的

本書は、安芸高田市の“いまの空気”と“暮らしの解像度”を伝える、個人運営のローカルメディア「あきたかたノート」の初期開発に向けて、プロダクトの目的、対象ユーザー、提供価値、MVP範囲、主要要件、非機能要件、成功指標を定義するものである。
本書は、プロダクト構想メモおよび設計思想を具体的な開発要件に落とし込むための文書として位置づける。

本PRDの主な用途は以下の通りである。

* 開発対象のスコープを明確にする
* MVPで実装すべき範囲と後続フェーズを分ける
* デザイン、情報設計、データ設計、技術設計、運用設計の前提を揃える
* Claude Code / Codex 等を含む実装チームへの引き継ぎ資料とする

⸻

## 2. プロダクト概要

### 2-1. プロダクト名

あきたかたノート

### 2-2. プロダクトの定義

本プロダクトは、安芸高田市の“いまの空気”と“暮らしの解像度”を、写真・動画・場所・時期・テーマ・短い解説を通じて伝える、個人運営のローカルメディアである。
一般的な観光案内サイト、行政広報、個人ブログ、SNSとは異なり、現地の一次的な感覚を残しつつ、投稿を知識資産として再発見できる構造を持つことを特徴とする。

### 2-3. 初期フェーズの前提

初期フェーズでは、運営者本人が現地で撮影・記録したコンテンツを中心に構成する。
将来的には参加型要素を拡張する可能性があるが、MVPではまず、写真中心の投稿体験、探索可能なアーカイブ構造、軽量な投稿運用、AIによる投稿補助を成立させることを優先する。

### 2-4. 立場と運営方針

本プロダクトは個人運営サイトであり、行政の公式見解や公式情報発信を代替するものではない。
必要に応じて公式情報への導線を持つことはあっても、サイト自体は非公式の個人メディアとして設計・運営する。
また、運営者の公的肩書きはサイト上に表示しない。

⸻

## 3. 背景と課題認識

安芸高田市のような地域の魅力は、単なる観光情報や施設情報では伝わりにくい。
地域の風景、季節感、人の営み、移動感覚、日常の温度感などは、現地にいるからこそ見える価値である一方、既存の情報発信手段では以下の課題がある。

* 公式情報は正確だが、空気感や暮らしの実感が伝わりにくい
* 観光案内サイトは定型的になりやすく、日常の魅力や現地性が薄くなりやすい
* SNSは即時性が高いが、投稿が流れやすく、知識資産として蓄積されにくい
* 外部の人にとって、場所、距離感、行き方、季節の違いなどが分かりにくい
* 写真や短い記録があとから「場所」「時期」「テーマ」で辿れない
* 投稿本数が少ない段階では、地図や分類導線が成立しにくい
* 個人運営であることと、公式情報との距離感を設計に落とし込む必要がある
* 写真中心サイトである以上、位置情報、人物写り込み、肖像権・著作権への配慮を運用に組み込む必要がある
* 日本語話者以外の関心層に対して、入口となる情報が不足しやすい

本プロダクトは、これらの不足を補い、地域の魅力を“空気感を持った知識資産”として蓄積・再発見できる場をつくることを目指す。

⸻

## 4. 目的

### 4-1. プロダクト目的

安芸高田市に関心を持つ外部ユーザーに対して、現地の温度感を伴う情報を届け、地域理解の入口をつくる。
また、投稿を単発で終わらせず、場所・季節・テーマなど複数の文脈で再発見できるように整理し、継続的に蓄積可能なローカルアーカイブを構築する。

### 4-2. 初期フェーズの到達目標

MVPでは、以下の状態を実現する。

* 写真中心の投稿が継続的に蓄積できる
* 投稿が地図・季節・テーマなどから探索できる
* 投稿1件に対して、場所・時期・背景・関連情報を付与できる
* 投稿作成時にAIが下書き・要約・分類補助などを支援できる
* スマートフォン中心で閲覧・投稿しやすい
* 少ない投稿数でも、サイト全体として成立した体験が保たれる
* サイト全体として「観光パンフレット」でも「単なるブログ」でもない体験が成立している
* 外部検索やSNS共有から個別投稿へ自然に着地できる
* 日本語中心の運用を保ちながら、固定ページや基本導線については将来的な英語対応を阻害しない

⸻

## 5. 非目的

初期フェーズでは、以下を目的としない。

* 一般ユーザーが自由に投稿できるUGCプラットフォーム化
* コメント機能やコミュニティ機能の本格実装
* 大規模な動画配信基盤の構築
* 交通情報や営業情報などの網羅的な公式情報集約
* 高度なAIチャット案内機能の提供
* 地域全体を包括的に説明し尽くす百科事典的サイト化
* 公的な立場を前面に出したブランド設計
* 高頻度更新を前提としたニュースメディア化
* 全投稿の完全な多言語運用
* 多言語SEOの本格運用

本プロダクトは、まず「現地の空気感を持った一次的な記録を、探索可能な構造で蓄積する」ことに集中する。

⸻

## 6. 想定ユーザー

### 6-1. 主対象ユーザー

A. 外から安芸高田市に興味を持つ人

* 名前や話題は知っているが、具体的なイメージは薄い
* 写真や風景、地域の話題をきっかけに関心を持つ
* 地域そのものの雰囲気を知りたい

B. 移住・関係人口候補

* 暮らしやすさや日常の温度感を知りたい
* 交通、距離感、人の気配、文化などを知りたい
* 公式情報だけでは見えない生活の解像度を求めている

### 6-2. 副次的ユーザー

* 安芸高田市民
* 地域づくりやローカルメディアに関心のある人
* 地方移住・関係人口づくりに興味がある人
* 日本語話者以外の海外の関心層

⸻

## 7. 提供価値

### 7-1. 現地性

現地で撮影された写真・動画・メモにより、その場の空気感、時間、移動の感覚、季節の表情を伝える。

### 7-2. 再発見性

投稿を時系列に流すだけでなく、場所、季節、テーマなど複数の切り口から再発見できる。

### 7-3. 理解補助

写真だけで終わらず、場所、行き方、背景、関連情報、公式導線を適切に付与することで、外部ユーザーの理解を助ける。

### 7-4. 継続性

投稿運用を重くしすぎず、軽量投稿とAI補助を活用することで、現地記録を継続して蓄積できる。

### 7-5. 発見可能性

サイト内の探索導線だけでなく、検索エンジンやSNS共有からも個別投稿へ到達できることで、外部ユーザーの入口を広げる。

### 7-6. 開かれた入口

日本語中心のローカルメディアでありながら、固定ページや基本導線については限定的な英語対応余地を持つことで、海外の関心層にも閉じすぎない入口をつくる。

⸻

## 8. コアユースケース

### 8-1. 閲覧系ユースケース

1. ユーザーはトップページから、安芸高田市の“今の雰囲気”を感じる
2. ユーザーは地図から、気になる場所の投稿を探す
3. ユーザーは季節やテーマから、興味に合う投稿をたどる
4. ユーザーは投稿詳細ページで、写真・背景・行き方・関連情報を見る
5. ユーザーは関連投稿をたどりながら、地域理解を深める
6. ユーザーは検索エンジンやSNS共有から個別投稿へ着地し、そこから探索を始める
7. 必要に応じて、ユーザーは英語の固定ページや基本導線からサイトの趣旨を把握できる

### 8-2. 投稿運用系ユースケース

1. 運営者はスマホで撮影した写真をアップロードする
2. システムは画像メタデータから取得可能な情報（日時、位置情報等）を補助的に扱う
3. システムは場所候補や時期候補を提示する
4. AIはタイトル、説明文、要約、タグ候補、カテゴリ候補を生成する
5. 必要に応じて、AIは英語説明文や翻訳ドラフトを補助生成する
6. 運営者は必要最小限の編集を行い、下書き保存または公開する
7. 投稿は地図・季節・テーマなどの導線に反映される
8. 必要に応じて、後から分類や説明を追加して整形する

⸻

## 9. MVPスコープ

### 9-1. MVPで実装するもの

コンテンツ閲覧

* トップページ
* 投稿一覧
* 投稿詳細ページ
* 地図からの閲覧導線
* 季節別・テーマ別の閲覧導線
* 新着導線
* 関連投稿表示
* 少量投稿でも成立する導線・UI設計

コンテンツ投稿

* 投稿作成
* 写真アップロード
* 場所情報の入力または補助
* 下書き保存 / 公開切替
* 投稿編集
* 軽量投稿と通常投稿を同一データ構造上で扱えること

投稿モード

* 軽量投稿モード
    写真1枚以上 + 短いメモ + 場所情報を中心に素早く残せる
* 通常投稿モード
    タイトル、説明文、要約、季節、テーマ、補足情報まで含めて整形できる

AI補助

* タイトル候補生成
* 説明文ドラフト生成
* 要約生成
* タグ候補生成
* カテゴリ / テーマ候補生成
* title / description の補助生成
* 固定ページや必要箇所に限った英語説明文 / 翻訳ドラフトの補助生成

基本情報付与

* 場所名
* 緯度経度または地図表示用位置情報
* 撮影時期 / 投稿日時
* 関連リンク
* 行き方や補足情報の手動記載
* AI補助テキストの保持

発見可能性 / SEO

* 固有URLを持つ投稿詳細ページ
* OGP設定
* title / description 設定
* sitemap.xml
* robots.txt
* 基本的な構造化データ
* 検索エンジンやSNS共有からの着地を前提としたメタ情報管理

公開前確認

* 公開前チェック項目を確認できる画面または確認ステップ
* 機械処理済み項目と人確認項目が区別されること
* 確認を完了してから公開できること

限定的な英語導線

* About等の固定ページに英語版を追加できる構造
* ナビゲーションやフッター等の固定文言を将来的に英語化できる実装前提
* 必要に応じて限定的な英語説明を持てること

基本UI/UX

* スマホ最適化
* 写真中心UI
* 静かなギャラリー × ローカルフィールドノートのデザイントーン
* 非公式の個人メディアとして誤認されにくい表示

### 9-2. MVPでは見送るもの

* 一般ユーザー投稿機能
* コメント、いいね、フォロー等のSNS的機能
* 匿名質問機能
* 高度なAIチャット
* 動画の本格ホスティング / 配信最適化
* 外部公式情報の自動クローリング連携
* パーソナライズレコメンド
* 全投稿の完全多言語対応
* 多言語SEOの本格実装
* 高度な分析ダッシュボード
* PWAによる本格的なオフライン下書き
* OSM/オープンデータとの高度なID連携
* RSS/Atom の厳密実装（ただし将来拡張を阻害しない構造とする）
* 高機能な審査ワークフローや承認フロー

## 10. 機能要件

### 10-1. トップページ

トップページは、サイト全体の空気感と探索導線の両方を担う。
以下の要素を持つことを想定する。

* キービジュアルまたは注目投稿
* 新着投稿
* 地図で見る導線
* 季節で見る導線
* テーマで見る導線
* このサイトについての簡易説明
* 個人運営サイトであることが分かる導線
* 将来的に固定文言を英語化しやすい構造

### 10-2. 投稿一覧機能

ユーザーが投稿を一覧的に見られること。
一覧は、単なる新着順だけでなく、テーマや季節などで絞り込み可能であることが望ましい。
また、探索UIを補完する形で、検索エンジンや共有導線に耐える一覧構造を持つことが望ましい。

### 10-3. 地図閲覧機能

投稿に紐づく位置情報をもとに、地図上から投稿へアクセスできること。
土地勘のないユーザーでも、場所ベースで投稿を探索できることを重視する。
初期の投稿数が少ない段階でも、体験が過度に貧弱に見えない表示方法を検討すること。

### 10-4. 季節・テーマ閲覧機能

ユーザーが季節やテーマから投稿を辿れること。
同じ場所でも異なる時期の表情が見えることが望ましい。
なお、季節・テーマの語彙は固定済み前提ではなく、初期仮投稿を通じて検証・調整する。

### 10-5. 投稿詳細機能

投稿詳細ページでは、以下の要素を表示できること。

* 写真
* タイトルまたは短いメモ
* 本文
* 要約
* 場所
* 時期
* タグ / カテゴリ / テーマ
* 補足情報
* 関連リンク
* 関連投稿
* OGP / SEO に利用される基本メタ情報

### 10-6. 投稿作成・編集機能

運営者が、写真中心で投稿を作成・編集できること。
下書き保存と公開切替に対応すること。
また、軽量投稿と通常投稿の両方を扱えること。

投稿の最小単位

下書きの最低要件

* 写真1枚以上
* 場所情報
* 作成日時
* 短いメモは空欄でも可

軽量投稿の公開最低要件

* 写真1枚以上
* 場所情報
* タイトルまたは短いメモ
* title / description を生成可能であること
* 季節またはテーマの少なくともどちらか一方、もしくは仮分類を持つこと
* 公開前チェックを完了していること

通常投稿の公開最低要件

* 写真1枚以上
* 場所情報
* タイトル
* 本文または説明文
* 季節またはテーマ
* title / description
* 公開前チェックを完了していること

不足する title / description は、AIまたはテンプレート補助で生成してよいが、人が確認することを前提とする。

### 10-7. AI補助機能

投稿作成時に、写真や入力メモをもとに、タイトル、説明文、要約、タグ、カテゴリ候補を補助生成できること。
AI出力はあくまで候補であり、人が確認・修正できることを前提とする。
また、AIが関与したテキストや翻訳ドラフトの扱いは、09_risk_ai_policy.md と整合するようにする。

### 10-8. 関連導線機能

個別投稿から、同じ場所、同じ季節、同じテーマなどの関連投稿に自然に遷移できること。

### 10-9. 個人運営表示機能

サイト内の適切な位置に、個人運営サイトであることが伝わる表示導線を持つこと。
Aboutページ、フッター、OGP等で、行政公式と誤認されないことを重視する。
なお、運営者の公的肩書きは表示しない。

### 10-10. メディア公開安全要件

画像公開時に、位置情報、EXIF、人物写り込み等に関する確認と安全配慮が行えること。
機械的に除去・分離できるものは技術的に処理し、公開判断が必要なものは運用フローで扱う。

### 10-11. 公開前チェック補助

MVPでは、高機能な審査ワークフローまでは実装しないが、少なくとも以下を満たす確認補助を持つ。

* 公開前にチェック項目を一覧できる
* EXIF/GPS除去など機械処理済み項目を確認できる
* 人物、私有情報、OGP妥当性、位置情報精度など人確認項目をチェックできる
* チェック未完了のまま公開できない、または強い注意が表示される

### 10-12. 限定的な多言語対応余地

MVPでは、全投稿の完全多言語運用は行わない。
一方で、少なくとも以下を満たすことが望ましい。

* 固定ページに英語版を追加可能であること
* 固定文言をロケールごとに分離可能であること
* 投稿データやメタデータの持ち方が、将来的な翻訳フィールド追加を阻害しないこと

⸻

## 11. 非機能要件

### 11-1. デバイス要件

* スマートフォンでの閲覧を最重要とする
* 投稿作成もスマートフォン中心で利用できること
* PCでも快適に閲覧・管理できること

### 11-2. 表示品質

* 写真が美しく見えること
* 情報を詰め込みすぎず、余白を活かした表示であること
* デザイントーンは静かで洗練されていること
* 行政公式サイトや観光パンフレットと誤認されにくいこと

### 11-3. パフォーマンス

* 主要ページの表示が極端に遅くならないこと
* 写真読み込みが体験を阻害しないこと
* モバイル回線でも実用的な表示速度を保つこと

### 11-4. 運用性

* 投稿作成に過度な手間がかからないこと
* AI補助により、記録から公開までの負荷を減らせること
* 軽量投稿から後編集で整えていけること
* データ追加によって地図・季節・テーマ導線が自然に育つこと
* 少ない投稿数でも体験が崩れにくいこと
* 英語対応を追加する場合でも、日本語中心の運用継続性を損なわないこと

### 11-5. 拡張性

* 将来的な参加型機能追加を見据えた構造を持つこと
* データ構造が、後の導線追加や特集化に耐えられること
* URLやデータ構造が将来的な資産性を損なわないこと
* 将来的な限定的i18n対応を阻害しないこと

### 11-6. 発見可能性

* 個別投稿が検索エンジンにインデックス可能な構造を持つこと
* SNS共有時に内容が適切に伝わるメタデータを持つこと
* サイトマップや構造化データ等、基本的なSEO要件を満たすこと

### 11-7. 安全性

* 公開画像から不要な位置情報が露出しないこと
* 人物、私有情報、生活導線の露出に配慮できること
* 公開前に確認可能な仕組みまたは運用があること

### 11-8. アクセシビリティ

* 主要画像に適切な代替テキストを付与できること
* キーボード操作やフォーカス移動に大きな支障がないこと
* 文字と背景のコントラストが不足しないこと
* 外から来た人が情報を理解しやすい、読みやすい構造を持つこと

⸻

## 12. UX要件

本プロダクトのUXは、以下を満たすことを目標とする。

* 初見ユーザーでも「どこで」「いつの」「何の話か」が直感的に分かる
* 写真から興味を持ち、必要に応じて情報を深掘りできる
* 地図、季節、テーマ、新着の複数導線から迷わず入れる
* 投稿1件が次の投稿への発見につながる
* 投稿数が少なくても、サイトとしての体験が成立している
* 投稿者にとって、現地での記録から公開までの流れが軽い
* 検索エンジンや共有導線から着地したユーザーにも理解しやすい
* 固定ページや基本導線については、将来的に英語話者にも最低限意味が伝わる拡張余地を持つ

⸻

## 13. デザイン要件

本プロダクトのデザインコンセプトは「静かなギャラリー × ローカルフィールドノート」とする。
これに基づき、以下を要件とする。

* 写真を主役とする
* 文章は補助として静かに配置する
* 派手な観光訴求より、余白と可読性を優先する
* 地図・季節・テーマ導線が自然に見つかる
* スマホ閲覧時にも空気感が損なわれない
* 個人メディアとしての距離感を保ち、公式と誤認されにくいこと

実装面では、現時点で以下を想定する。

* Tailwind CSS ベース
* 必要箇所に shadcn
* 本文フォント: Noto Sans JP
* 見出しフォント: Zen Kaku Gothic New

⸻

## 14. 技術前提（初期方針）

詳細な技術選定は後続の技術設計概要および技術選定メモで定義するが、MVPでは以下のような方向性を想定する。

* フロントエンド / アプリケーション基盤: モダンなReact系フレームワーク
* コンテンツ管理: Headless CMS または構造化コンテンツ管理を前提とする
* 画像管理: 画像最適化と公開用変換が可能な仕組みを持つ
* 地図: コストと柔軟性のバランスが取れたWeb地図基盤を利用する
* AI: 編集補助用途に適した外部APIを利用する
* ホスティング / 配信: モバイルでも快適な配信と継続運用しやすい構成を採用する
* 固定文言や固定ページは、将来的にロケール分離しやすい構造を意識する

この段階では、詳細製品名の確定よりも、設計思想に合う構成要件を揃えることを優先する。

## 15. AI要件・制約

### 15-1. AI利用目的

* 説明文下書き生成
* 要約生成
* タイトル候補生成
* タグ・カテゴリ候補生成
* 関連情報候補生成
* 固定ページや必要箇所に限った翻訳ドラフト補助

### 15-2. AI利用上の制約

* AI生成結果は自動公開しない
* 人が確認・修正できる前提とする
* 営業時間、交通情報、制度情報などの断定的記述には慎重であること
* 地域の価値観や暮らしをAIが代表して語る構造にしない
* AIが関与したテキストの扱いは、運用ルールとして定める
* AI生成文やAI翻訳の表示要否や責任境界は、リスク・AI方針で詳細化する

## 16. 成功指標（初期案）

MVP段階では、PVの多寡だけでなく、プロダクトの成立性と運用継続性を重視する。
初期の指標候補は以下とする。

### 16-1. コンテンツ蓄積

* 公開投稿数
* 月間投稿本数
* 地図上に可視化されるスポット数
* 季節 / テーマ分類が付与された投稿割合
* 軽量投稿から整形投稿へ更新された件数

### 16-2. 閲覧体験

* 地図経由の閲覧数
* 季節 / テーマ導線の利用率
* 投稿詳細への到達率
* 関連投稿への遷移率
* 再訪率
* 外部検索や共有からの着地数

### 16-3. 運用体験

* 1投稿あたりの作成時間
* AI補助利用率
* 下書きから公開までの完了率
* 現実的な投稿頻度でもサイト体験が維持できているか

### 16-4. プロダクトらしさの確認

* 「現地の空気感が伝わる」と感じられるか
* 「観光案内サイトやブログとは違う」と感じられるか
* 「あとから探し直しやすい」と感じられるか
* 「少ない投稿数でも成立している」と感じられるか

※ 定性的評価も初期は重要とする。

## 17. リスクと留意事項

本プロダクトには、以下のような留意点がある。

* 個人運営サイトであることが誤解なく伝わること
* 行政公式サイトと誤認されないこと
* 肖像権、著作権、位置情報、人物写り込み、私有情報の扱いに注意すること
* 公開画像から不要なEXIF/GPS情報が露出しないこと
* 古い交通情報や施設情報を断定しないこと
* AI生成文による誤解を防ぐこと
* AI翻訳による誤解を防ぐこと
* 公私の境界を越える内容を扱わないこと
* 投稿参加を広げる場合は品質維持とルール設計が必要であること

これらは今後、以下の後続文書で詳細化する。

* 公私区分・対外表記方針
* SEO・メタデータ方針
* 写真・位置情報公開ポリシー
* リスク・AI方針

## 18. 今後の後続ドキュメントとの関係

本PRDをもとに、以下を具体化する。

* 技術設計概要
    実装技術、コンテンツ管理、画像配信、地図、AI、ホスティング等の方向性を定義する
* 技術選定メモ（ADR）
    フレームワーク、CMS、画像配信、地図、AI等の主要技術選定理由を記録する

    地図・季節・テーマ・新着を軸とした導線と、検索流入に耐えるページ構造を定義する
* データ設計書
    投稿、場所、タグ、分類語彙、メディア、関連リンク等の構造を定義する
* 分類語彙設計メモ
    季節・テーマ・タグの役割分担と初期語彙案、仮投稿検証方法を定義する
* コンテンツ運用設計
    撮影から下書き、AI補助、公開、後編集までの運用フローを定義する
* 公私区分・対外表記方針
    個人運営サイトとしての表記ルール、肩書き非表示方針、誤認防止方針を定義する
* SEO・メタデータ方針
    OGP、構造化データ、サイトマップ、URL等の扱いを定義する
* 写真・位置情報公開ポリシー
    EXIF、GPS、人物写り込み、私有情報等の扱いを定義する
* リスク・AI方針
    AI表示ルール、誤情報防止、公開責任、公私衝突時の判断基準への対応を定義する
* 進め方ロードマップ
    文書整備、仮投稿検証、ADR、実装着手までの進行順を定義する
