# 情報設計書（IA）

## 1. 文書の目的

本書は、「あきたかたノート」の画面構造・導線・URL階層を定義する。
ロードマップ Step 8 に対応し、`12_data_model.md` のエンティティ（Post / Place / Season / Theme / Tag / Media / Link / StaticPage ＋ SafetyReview / PublishChecklist）を、人向けの探索体験と機械向けの階層構造の両方へ展開する。

前提とする確定文書

* 設計思想・トーン: `02_design_principles.md`
* 公私区分・非公式性の表示: `05_public_private_policy.md`
* 分類語彙（季節・テーマ・タグ・Place）: `06_taxonomy_design.md`
* SEO / URL / 構造化データ: `07_seo_metadata_policy.md`
* 写真・位置情報・地図導線: `08_photo_location_policy.md`
* データモデル: `12_data_model.md`

⸻

## 2. 設計原則

* **写真主役・静かなギャラリー**: 文章は補助、余白を活かす（`02`）。
* **探索性 > 一覧性**: 場所・季節・テーマ・地図の複数文脈から再発見できることを優先する。
* **人には探索的に、機械には階層的に**: 閲覧者にはゆるやかな回遊を、検索エンジンには `/posts` `/theme/{slug}` `/season/{slug}` `/place/{slug}` の安定した階層を見せる（`07 §2-2 / §9`）。
* **スマホ最優先**: 閲覧も投稿もモバイルを第一に設計する。
* **少量投稿でも成立**: 投稿が10〜20本でも導線が破綻しない初期UIを持つ（少量時方針は §8）。
* **安全をUIで担保**: 地図表示・公開判断・公開前チェックは、データ構造（公開レベル・SafetyReview・PublishChecklist）に従って表示・制御する（`08`、`12`）。

⸻

## 4. URL構造

人が読んで意味が分かり、将来も安定する階層を基本にする（`07 §9`）。

公開側

* `/` トップ
* `/posts` 投稿一覧（新着順）
* `/posts/{slug}` 投稿詳細（タイトル or 場所＋要約ベースの可読スラッグ。自動IDのみは避ける）
* `/place/{slug}` Place詳細
* `/theme/{slug}` テーマ一覧（slug は語彙に対応: 自然 / 文化 / 日常 / イベント / 食 / 移動・行き方）
* `/season/{slug}` 季節一覧（春 / 夏 / 秋 / 冬 / 通年）
* `/map` 地図
* `/about`、`/{固定ページ}` 固定ページ

タグの一覧URL（`/tag/{slug}`）は **MVPでは設けない**。タグは投稿詳細・Place詳細での**表示のみ**の補助情報とし、主導線は季節・テーマ・場所・地図とする（`06 §7-1`）。これは語彙の散らかりと thin な一覧ページの増殖を避けるため。将来タグページを設ける場合のみ、Theme/Season と同じ slug 方針を適用する（`12 §8`）。

管理側（noindex）

* `/admin/posts/{id}/edit` 投稿編集
* `/admin/posts/{id}/review` 公開前チェック
* `/admin/places/{id}` Place管理

slug の責務はデータモデル側に持つ: Post / Place は slug フィールド、Theme / Season はクローズド語彙の各値に対応する安定 slug（`12_data_model.md §4-1 / §4-2 / §4-3 / §4-4`）。slug は内部ID・表示名と分離し、表示名を変えてもURLを保つ。

将来の英語固定ページは `/en/about` のようなロケールベースへ拡張可能にする（`07 §9-4`、本書 §7）。日本語URLの是非（例: `/theme/移動・行き方` か `/theme/mobility` か）は技術設計（Step 9 ADR）で確定する（`12 §8`）。

⸻

## 5. 各画面の構造

### 5-1. トップ

* 主役は最新投稿の写真（大きめのビジュアル）。
* そこから4つの探索入口へ分岐: **地図 / 季節 / テーマ / 新着**（`03` MVP導線）。
* 季節・テーマは語彙チップで提示し、各 `/season/{slug}` `/theme/{slug}` へ。
* 一覧性より探索性を優先し、全件羅列はしない。
* 構造化データ: WebSite / 代表画像。パンくず起点。

### 5-2. 投稿詳細（`/posts/{slug}`）

写真を主役に、補助情報を下に積む。

* 写真（Media、複数は order 順。スワイプ/縦スクロール、スマホ最適化）
* タイトル / 一言メモ（軽量は短文可）
* 本文 / メモ
* メタ: 季節（→ `/season/{slug}`）、テーマ（複数、→ `/theme/{slug}`）、タグ（**表示のみ・リンク先なし**。MVPでは一覧ページを持たない）、時間帯、撮影日
* 場所: Place名（→ `/place/{slug}`）、地図（**公開レベルに従う**。§5-6）
* 関連リンク（Link、公式情報への導線）
* 関連投稿: 同じ Place / 同じテーマ / 同じ季節への回遊（検索流入後の回遊は §6）
* 構造化データ: 記事相当（タイトル・概要・公開日・画像・URL、事実ベース。`07 §7`）
* OGP画像: **`SafetyReview.ogp_ok = true` の代表画像**を使う。該当画像が無ければ**サイト既定のOGP画像にフォールバック**（本文画像を無条件流用しない。`07 §6-2`、`12 §4-10`）。
* 表示は `PublishChecklist` 通過済み（status=公開）の投稿のみ。

### 5-3. Place詳細（`/place/{slug}`）

Post と Place の分離を活かし、同じ場所の異なる時期・テーマを束ねる（`06 §4`、`12 §4-2`）。

* Place名 / 表示名 / 補足
* 地図（**`base_location_level` に従う**。§5-6）
* そのPlaceに紐づく投稿一覧（季節・時期で並べ替え可能 → 「同じ場所の四季」が成立）
* place_tags（例: 温泉街）は場所属性として表示（投稿タグとは別。`06 §7-6`）
* レベルC/Dの Place は地図を出さず地名・地区名に留める（§5-6）。

### 5-4. テーマ一覧 / 季節一覧（`/theme/{slug}`, `/season/{slug}`）

* 該当する投稿をカード（写真＋タイトル＋場所＋季節/テーマ）で提示。
* テーマは複数付与され得るため、1投稿が複数テーマ一覧に現れる（`06 §6-7`）。
* フィルタはMVPでは最小限（季節×テーマの掛け合わせは将来検討）。
* 構造化データ: CollectionPage 相当。パンくず: トップ > テーマ/季節 > 当該。

### 5-5. 投稿一覧（`/posts`）

* 主に機械向けの階層的入口（新着順）。人向けにはトップの探索導線を優先。
* サイトマップ・パンくずの幹（`07 §2-2 / §8`）。

### 5-6. 地図（`/map`）と地図導線

地図は主要導線である一方、位置情報リスクの入口でもある（`08 §5-4`）。表示はデータの公開レベルに厳密に従う。

* ピンは Place 単位。ピン位置は**撮影地点そのものではなく代表地点**（`08 §5-4`）。
* 公開レベル別の表示制御（`08 §5-2`、`12 §6`）:
  * **A**: 正確な代表地点をピン表示
  * **B**: おおよその地域表示（ピンをぼかす/エリア表示）
  * **C**: 地図ピンを出さず地名・地区名のみ
  * **D**: 地図非表示 / 地図導線に載せない
* `map_display = false` の投稿・Placeは地図に出さない。
* ピン → Place詳細 → 投稿、という階層で「地図ピン背後の階層URL」を構成する（`/place/{slug}` が地図とページの接続点）。

### 5-7. サイト共通導線（グローバルナビ / フッター）

全画面に共通するヘッダー・フッターは、探索導線の常設と「個人運営・非公式」の誠実な表示を両立させる（`05`）。

ヘッダー（グローバルナビ）

* サイト名「あきたかたノート」（→ トップ）。
* 主要探索導線: 地図 / 季節 / テーマ / 新着。スマホでは最小化（ハンバーガー、または下部固定の最小タブ）。
* 写真主役を邪魔しない静かなヘッダー（`02`）。行政公式と誤認させる配色・ロゴ・権威的表現は避ける（`05 §2-6`）。

フッター（非公式性・About・ポリシー）

* **個人運営メディアである旨を明示**し、「運営者個人による記録であり、行政・自治体の公式見解を代表しない」を継続表示する（`05 §2-1`（個人運営）/ §3-3（公的見解との切り分け）/ §6-3（フッター））。
* 運営者表示名は「**コバッチ**」。**公的肩書きは一切出さない**（`05 §2-3 / §4-3`）。
* About / 運営方針 / 写真・位置情報への配慮 / 利用上の注意 への導線（`StaticPage`。`05`・`08`）。
* 必要に応じて連絡導線（問い合わせ）。
* フッター文言と About を一貫させ、OGP・SNS共有時にも非公式性が保たれるようにする（`05 §2-6`、`07 §1 / §6`）。
* 将来の英語固定ページ導線（`/en/about` 等）をフッターから出せる構造にする（§7、`07 §9-4`）。

⸻

## 6. 検索流入後の回遊

検索からの着地（多くは投稿詳細）から、行き止まりにしない（`07 §2`）。

* 投稿詳細に「同じ場所（Place）」「同じテーマ」「同じ季節」への導線を常設。
* Place詳細へ誘導し、「この場所の他の時期/テーマ」へ広げる。
* パンくず（トップ > テーマ/季節/Place > 投稿）で上位階層へ戻れる。

⸻

## 7. 固定ページと英語導線

* About等は `StaticPage`。運営方針・公私区分の明示（`05`）、写真/位置情報への配慮の説明を含む。
* 英語対応はMVP必須ではないが、トップ・About・固定ページは将来 `/en/...` を持てる構造にする（`07 §9-4`、`12 §4-8` locale_fields）。
* 英語導線を出す場合もコンテンツ本体（投稿）は当面日本語のみ（`07 §2-3`）。

⸻

## 8. 少量投稿時のUI方針

仮投稿20本規模でも導線が成立すること（`03`、`13` の検証を踏まえる）。

* 地図: ピンが少なくても地域の広がりが見えるズーム初期値。空エリアでも破綻しない。
* テーマ/季節一覧: 0〜数件でも成立するレイアウト（「まだ少ない」状態を恥じないトーン）。
* トップ: 新着が少なくても写真主役で成立。
* 季節は春偏在・夏秋ゼロ（`13 §5`）でも、空の季節タブを「これから」と示せる扱い。

**空ページのSEO上の扱い（UI表示と検索可視性を分ける）**:

* 投稿0件のテーマ/季節/Place一覧ページは、**UI上は導線として表示する**（語彙の存在を示し、回遊の入口を欠かさない）。
* ただし検索上は thin content になるため、**0件ページは noindex＋sitemap除外**とし、**該当投稿が1件以上になったら index 対象に戻す**（`07 §8-3`）。判定は投稿件数で機械的に行う。

⸻

## 9. 公開前チェックUI（管理側）

`12_data_model.md` の二層（SafetyReview / PublishChecklist）をそのまま画面化する。安全を運用規律でなくUIのゲートで担保する（`08 §11`）。

### 9-1. 画像ごとの安全確認（SafetyReview。`12 §4-10`）

投稿に紐づく各 Media をサムネイルで並べ、画像ごとに確認項目を持つ。

| 項目 | UI挙動 |
|---|---|
| exif_gps_ok | 自動。派生生成＋検査の結果を表示（人の操作項目にしない。`08 §11-4`）。未除去なら赤表示 |
| face_ok | AI顔検出の枠を画像上に提示。運用者が「不要/確定（ぼかし/トリミング/差し替え後）」を選ぶ。自動で確定にしない（`08 §11-5`） |
| child_minor_ok / nameplate_plate_ok / private_life_ok / landmark_level_ok / ogp_ok | チェックボックス（未確認→確認済）。各項目に `08` の該当条文をツールチップ表示 |

* 画像が「安全確認済み」になるのは exif_gps_ok=true かつ face_ok が不要/確定かつ人手項目がすべて確認済のとき。
* スマホ前提: AIが付けた枠をタップ確認する程度の軽さに収める（`08 §11-5` の運用継続性）。

### 9-2. 投稿の公開ゲート（PublishChecklist。`12 §4-11`）

投稿単位で公開可否を集約する。

* `media_safety_cleared`: 全 Media の SafetyReview 完了から自動算出（1枚でも未確認なら未充足）。
* `map_display_ok` / `location_level_ok`: 運用者が確認（地図表示の妥当性、公開レベルの妥当性。`08 §5-2` の「画像内ランドマークでの特定」も含めて判断）。
* **公開ボタンは全項目充足まで無効**（status=公開へ遷移不可。`12 §5-1` の公開ゲート）。
* 未充足項目は一覧で赤表示し、`08 §10-3` の対応優先順（差し替え→トリミング/マスク→レベル引き下げ→地図導線から外す→公開しない）への動線を添える。

### 9-3. 仮投稿検証との対応

`13_trial_verification_report.md` で挙げた要対応（trial-011 私有地、001 ナンバー、002/007 ランドマーク、018 人物、全画像のEXIF）は、それぞれ private_life_ok / nameplate_plate_ok / landmark_level_ok / face_ok / exif_gps_ok のゲートで止まる構造になる。

## 10. 構造化データ・パンくず・サイトマップ

* パンくず: トップ > （テーマ/季節/Place）> 投稿。各階層URLに対応（`07 §7`）。
* 構造化データは事実ベース。投稿=記事相当、一覧=CollectionPage相当、トップ=WebSite（`07 §7`）。
* サイトマップに公開投稿・一覧・テーマ/季節/Placeページを含め、管理・下書き・**投稿0件の一覧ページ**は除外（`07 §8`）。0件ページには noindex を付与する（`07 §8-3`、§8）。

⸻

## 11. レスポンシブ / 表示方針

* モバイルファースト。写真は縦スクロールで主役化、メタは折りたたみ可。
* フォント: 見出し Zen Kaku Gothic New / 本文 Noto Sans JP（`project` 方針）。Tailwind ＋ 必要箇所に shadcn/ui。
* 余白を活かした静かなレイアウト。派手な訴求は避ける（`02`）。
