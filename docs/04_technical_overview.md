# 技術設計概要（改訂版）

## 1. 文書の目的

本書は、「あきたかたノート」のMVP開発に向けて、技術的な前提、構成方針、主要コンポーネント、実装上の判断軸を整理するものである。
PRDで定義した機能要件・非機能要件を、実際に成立させるための技術構成の土台として位置づける。

本書の目的は、以下の通りである。

* MVPに必要な技術要素を明確にする
* 情報設計書、データ設計書、コンテンツ運用設計の技術前提を揃える
* Claude Code / Codex 等を含む開発チームが、実装時に判断を迷いにくくする
* 今後の技術選定メモ（ADR）で比較・確定する論点の整理を行う

本書は詳細設計書ではなく、MVP実装の方向性を固めるための技術方針文書 である。

⸻

## 2. 設計対象の前提

### 2-1. プロダクト特性

本プロダクトは、以下の性質を持つ。

* 写真中心のローカルメディアである
* スマートフォンでの閲覧・投稿が重要である
* 地図・季節・テーマによる探索性が重要である
* 投稿数が少ない初期段階でも体験が成立する必要がある
* AIは編集補助として利用する
* 個人運営サイトとして、非公式性を保つ必要がある
* 写真、位置情報、人物写り込みなどへの安全配慮が必要である
* 将来的に投稿数、導線、コンテンツ分類が育つことを前提とする
* 日本語中心で運用しつつ、固定ページや基本導線については将来的な限定的多言語対応余地を持つことが望ましい

### 2-2. MVPにおいて技術的に重視すること

MVPでは、以下を優先する。

* 投稿・閲覧の基本体験を素早く成立させること
* 写真表示品質とモバイル表示性能を確保すること
* 地図・分類導線をシンプルに成立させること
* 投稿運用の負荷を下げること
* 将来の拡張を妨げない構造を持つこと
* 運用・保守コストを過度に高くしないこと
* 将来の限定的i18n対応を阻害しないこと

⸻

## 3. 技術設計の基本方針

### 3-1. 静的配信を活かしつつ、更新性を持たせる

本サイトは、外部閲覧向けのコンテンツサイトであり、表示速度、SEO、共有時の安定性が重要である。
そのため、可能な限り静的生成またはそれに近い配信方式を活かしつつ、投稿更新時に反映しやすい構成を採る。

### 3-2. コンテンツ構造を先に立てる

本サイトは単なるブログではなく、投稿を場所・季節・テーマなど複数軸で再利用する。
そのため、画面実装より先に、構造化されたコンテンツ管理を前提とする。

### 3-3. 写真は「原本」と「公開用」を分けて扱う

写真中心のサイトであるため、表示品質・パフォーマンス・安全性の観点から、原本管理と公開画像配信を分離して考える。
特に、EXIF/GPS情報やサイズ最適化の観点から、公開時に適した変換経路を持つことを前提とする。

### 3-4. AIは前処理と編集補助に限定する

AIは、文章生成や分類補助に使うが、公開ロジックや事実判断の主体にはしない。
また、位置情報や日時など、機械的に取得可能な情報はAIの前段で処理する。

### 3-5. MVPでは複雑な自動化よりも、明快な運用可能性を優先する

将来的に高度な自動化や外部データ連携はありうるが、MVPではまず「投稿できる」「探せる」「安全に公開できる」を安定して回すことを優先する。

### 3-6. 多言語対応は“最初から全部やる”のではなく、“後から足せる構造”を優先する

MVPでは日本語中心の運用を前提とし、全投稿の完全多言語化は目標にしない。
一方で、固定文言、固定ページ、メタデータ、ルーティング、CMSフィールド設計については、将来的な限定的英語対応を追加しやすい構造を意識する。

⸻

## 4. 想定アーキテクチャ概要

MVP時点では、以下のようなレイヤ構成を想定する。

1. フロントエンド / Webアプリケーション層
    公開サイト、投稿管理UI、メタデータ出力、SEO対応、将来的な固定文言のロケール切替余地を担う
2. コンテンツ管理層
    投稿、場所、分類語彙、関連リンク等を構造化して保持する
3. メディア管理層
    写真アップロード、公開用変換、配信最適化を担う
4. 地図・位置情報層
    地図表示、位置情報の保持、逆ジオコーディング補助等を担う
5. AI連携層
    タイトル・説明文・要約・分類候補の生成補助、必要に応じた翻訳ドラフト補助を担う
6. ホスティング / 配信層
    サイト配信、キャッシュ、デプロイ、環境管理を担う
7. 運用 / 安全管理層
    表記方針、写真公開ポリシー、AI利用方針に基づく確認・運用を担う

⸻

## 5. 主要技術領域ごとの方針

### 5-1. フロントエンド / アプリケーション基盤

想定方針

* React系フレームワークを採用する
* SEO、OGP、構造化データ、動的メタ情報管理に対応しやすいことを重視する
* 静的生成またはそれに近い配信を活かしやすい構成を採る
* 投稿詳細、一覧、テーマ別、季節別、地図導線などを柔軟に構築できることを重視する
* 将来的な固定文言のロケール分離や限定的な英語ページ追加に対応しやすいことを重視する

現時点の有力候補

* Next.js（App Router）
* Astro
* Remix

現時点の第一候補

Next.js 系構成 を第一候補とする。
理由は以下の通り。

* SEO / メタデータ対応がしやすい
* ルーティングとページ構造を組みやすい
* 動的要素と静的要素のバランスが取りやすい
* 画像・OGP・構造化データ対応との相性が良い
* Reactベースで今後の拡張もしやすい
* 将来的な locale-aware なページ構成に拡張しやすい

ただし、最終決定は技術選定メモ（ADR）で行う。

⸻

### 5-2. UI実装方針

想定方針

* レイアウトや余白の微調整をしやすいこと
* 写真主役の静かなデザインを実装しやすいこと
* モバイルファースト設計に向いていること
* フィルタ、ドロワー、ダイアログなどの基本コンポーネントを効率よく組めること
* 固定文言を将来的にロケール辞書へ切り出しやすいこと

現時点の前提

* Tailwind CSS
* 必要箇所に shadcn
* 本文フォント: Noto Sans JP
* 見出しフォント: Zen Kaku Gothic New

方針

これは現時点で維持する。
MVPでは、デザインシステムを大規模に独自構築するよりも、Tailwindベースで余白・タイポグラフィ・カード構造を細かく制御する方針が適している。

⸻

### 5-3. コンテンツ管理方式

想定方針

本サイトでは、投稿・場所・分類語彙・関連リンクなどを、単なる記事本文ではなく、構造化されたデータとして扱いたい。
そのため、Markdown主体よりも、構造化コンテンツを管理しやすい方式 を優先する。

選択肢

* Markdown / Gitベース管理
* Headless CMS
* DB直接管理型

現時点の有力候補

* microCMS
* Sanity
* Supabaseベースの独自管理

現時点の第一候補

Headless CMS を第一候補とする。
理由は以下の通り。

* 投稿、場所、テーマ、季節語彙を分けて管理しやすい
* 将来的な再分類や構造変更に対応しやすい
* 管理画面を一から作り込まなくても一定の運用が可能
* 個人運営の継続性と運用負荷のバランスが良い
* 固定ページや一部コンテンツについて、多言語フィールドを持てる構造にしやすい

具体候補の考え方

* microCMS: シンプルで導入しやすい
* Sanity: 構造化の自由度が高い
* Supabase: 柔軟だが管理画面・運用設計の自前負荷が増えやすい

最終的には、以下を比較して決める。

* 初期運用負荷
* 構造化のしやすさ
* 将来の拡張性
* 固定ページやメタデータに対する限定的多言語対応のしやすさ

⸻

### 5-4. データモデルの大枠

MVP時点でも、最低限以下の概念を分けて持てる構造が望ましい。

* Post（投稿）
* Place（場所）
* Theme / Season / Tag（分類）
* Media（画像等）
* Link（関連リンク）
* StaticPage（固定ページ）またはそれに準ずる構造

基本方針

* Post と Place は分離を前提に考える
* 同じ場所に複数投稿が紐づけられる構造が望ましい
* 季節・テーマはタグと別役割で持つ
* 軽量投稿と通常投稿を同一の投稿エンティティ上で管理できるようにする
* 固定ページや一部メタ情報は、将来的に言語別フィールドを持てる余地を残す

詳細はデータ設計書で定義する。

⸻

### 5-5. 画像管理 / 配信

想定方針

写真は本プロダクトの中心要素であるため、以下を満たす必要がある。

* 表示速度が良い
* モバイルでも実用的
* サムネイルやサイズ変換が可能
* 公開用画像から不要なメタデータを落としやすい
* 原本と公開用を分けて扱える

選択肢

* Cloudflare Images
* Cloudinary
* オブジェクトストレージ + 変換基盤
* フレームワーク内の簡易画像最適化のみ

現時点の第一候補

画像最適化・変換・配信を担える専用サービスまたは同等構成 を前提とする。
MVPでは、フロントエンドだけで画像最適化を背負うのではなく、メディア層で処理する方針が望ましい。

画像に関する運用前提

* 原本保持の可否を決める
* 公開画像は必要に応じてメタデータ除去済みのものを使う
* 写真・位置情報公開ポリシーと整合させる
* OGPやサムネイル用画像を安全に切り出せることを考慮する

⸻

### 5-6. 地図 / 位置情報基盤

想定方針

本サイトでは、地図は主要導線のひとつである。
ただし、MVPでは高度なGIS機能ではなく、場所から投稿へ辿れること が主目的となる。

選択肢

* MapLibre + OSM系タイル
* Mapbox
* Google Maps

現時点の考え方

* コスト
* デザイン自由度
* ベンダーロックイン
* 位置情報・地図UIの扱いやすさ

を踏まえて比較する。

MVPに必要なこと

* 投稿地点を地図上で表示できる
* 投稿数が少なくても破綻しない
* 詳細地点の出しすぎに注意できる
* 地図導線がスマホで扱いやすい

位置情報の扱い

* 画像EXIF由来のGPS情報と、公開用の地図表示位置は分けて考える
* 必要に応じて精度を落として表示できるようにする
* 逆ジオコーディング等はAIの前段で処理可能なものとして検討する
* Place に位置情報公開レベルを持たせる拡張余地を意識する

⸻

### 5-7. AI連携

想定方針

AIは、編集補助用途に限定する。
用途は以下を想定する。

* タイトル案生成
* 説明文ドラフト生成
* 要約生成
* テーマ / タグ候補生成
* 関連情報候補生成
* 必要箇所に限った翻訳ドラフト生成

技術方針

* 画像・メモ・取得済みメタ情報を入力に使う
* AIの前段で取得可能な情報は先に抽出する
* AI出力は保存可能だが、自動公開しない
* 出力結果は人が確認・編集できることを前提とする

外部APIの考え方

* Claude API
* OpenAI API

などが候補となるが、MVPでは「編集補助に十分であること」「コストと運用が過度でないこと」を重視する。

追加前提

* AI出力の表示ルール、責任境界、公開方針は 09_risk_ai_policy.md と整合させる
* 翻訳ドラフトは固定ページや必要箇所に限定し、全投稿への自動適用は前提としない

⸻

### 5-8. ホスティング / 配信基盤

想定方針

* モバイルでも安定して速い
* 個人運営でもデプロイ・運用しやすい
* SEOやキャッシュ制御に不利でない
* 開発フローと相性が良い

候補

* Vercel
* Cloudflare Pages
* その他の静的配信 / エッジ配信基盤

現時点の考え方

フロントエンド基盤との親和性が高く、画像・地図・メタデータと合わせて運用しやすいものを優先する。
MVPでは、開発速度と安定性を重視する。

⸻

### 5-9. 認証 / 管理UI

想定方針

初期は個人運営前提のため、閲覧者向け認証は不要とする。
必要なのは投稿・編集・公開管理のための管理UIであり、これはCMS側の管理画面または限定的な専用管理UIで対応する。

MVPで必要なこと

* 投稿作成 / 編集 / 公開切替
* 画像アップロード
* 分類付与
* AI補助結果の確認
* 公開前確認
* 固定ページ編集
* 将来的な英語固定ページ追加を阻害しないこと

将来の拡張

* 招待制投稿
* 役割別権限
* 承認フロー

などは後続フェーズで検討する。

⸻

## 6. 技術的に考慮すべき横断論点

### 6-1. SEO / メタデータ

MVPでも、以下は技術的に成立させる必要がある。

* title / description のページ単位設定
* OGP
* sitemap.xml
* robots.txt
* 構造化データ
* 固有URL
* 共有時の安定したメタ情報

この詳細は 07_seo_metadata_policy.md で定義する。

⸻

### 6-2. 非公式性の表示

個人運営サイトであることを適切に表示するため、以下を技術的に扱える必要がある。

* Aboutページ
* フッター表記
* OGP説明文
* サイト説明文
* プロフィール導線

この詳細は 05_public_private_policy.md で定義する。

⸻

### 6-3. 写真公開の安全性

画像アップロードから公開までの間に、少なくとも以下を扱える必要がある。

* EXIF / GPS の扱い
* 公開用画像生成
* 必要な確認フロー
* 人物や私有情報の公開判断支援

この詳細は 08_photo_location_policy.md で定義する。

⸻

### 6-4. コンテンツ可搬性

本サイトは「資産として残す」ことを重視するため、CMSや特定プラットフォームに過度に閉じないことが望ましい。
MVP時点では完全な仕組みを作り込まなくてもよいが、将来的にエクスポートやバックアップを取りやすい構造を意識する。

⸻

### 6-5. 限定的i18n対応余地

MVPでは全投稿の完全多言語対応は前提としないが、少なくとも以下を技術的に阻害しないことが望ましい。

* 固定文言をロケール別に切り出せること
* 固定ページに英語版を追加しやすいこと
* 必要に応じて /en/... のような限定的ロケールルーティングへ拡張可能であること
* メタデータやCMS項目が将来的な英語フィールド追加を妨げないこと

⸻

## 7. 現時点で確定しないもの

以下は現時点では方向性のみ定め、詳細確定は後続文書で行う。

* フレームワークの最終選定
* CMSの最終選定
* 画像配信基盤の最終選定
* 地図基盤の最終選定
* AI APIの最終選定
* 逆ジオコーディングや自動分類補助の具体方式
* 原本保持の厳密方針
* オフライン下書き対応の要否
* RSS / Atom のMVP内外
* ロケールルーティングの具体方式
* 固定ページの英語管理方式
* hreflang 等の多言語SEO対応時期

これらは、技術選定メモ（ADR） で候補比較と採否判断を記録する。
