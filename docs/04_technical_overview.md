# 技術設計概要（改訂版）

## 1. 文書の目的

本書は、「あきたかたノート」のMVP開発に向けて、技術的な前提、構成方針、主要コンポーネント、実装上の判断軸を整理するものである。
PRDで定義した機能要件・非機能要件を、実際に成立させるための技術構成の土台として位置づける。

本書の目的は、以下の通りである。

* MVPに必要な技術要素を明確にする
* 情報設計書、データ設計書、コンテンツ運用設計の技術前提を揃える
* Claude Code / Codex 等を含む開発チームが、実装時に判断を迷いにくくする
* 今後の技術選定メモ（ADR）で比較・確定する論点の整理を行う

本書は詳細設計書ではなく、MVP実装の方向性を固めるための技術方針文書 である。

⸻

## 2. 設計対象の前提

### 2-1. プロダクト特性

本プロダクトは、以下の性質を持つ。

* 写真中心のローカルメディアである
* スマートフォンでの閲覧・投稿が重要である
* 地図・季節・テーマによる探索性が重要である
* 投稿数が少ない初期段階でも体験が成立する必要がある
* AIは編集補助として利用する
* 個人運営サイトとして、非公式性を保つ必要がある
* 写真、位置情報、人物写り込みなどへの安全配慮が必要である
* 将来的に投稿数、導線、コンテンツ分類が育つことを前提とする
* 日本語中心で運用しつつ、固定ページや基本導線については将来的な限定的多言語対応余地を持つことが望ましい

### 2-2. MVPにおいて技術的に重視すること

MVPでは、以下を優先する。

* 投稿・閲覧の基本体験を素早く成立させること
* 写真表示品質とモバイル表示性能を確保すること
* 地図・分類導線をシンプルに成立させること
* 投稿運用の負荷を下げること
* 将来の拡張を妨げない構造を持つこと
* 運用・保守コストを過度に高くしないこと
* 将来の限定的i18n対応を阻害しないこと

⸻

## 3. 技術設計の基本方針

### 3-1. 静的配信を活かしつつ、更新性を持たせる

本サイトは、外部閲覧向けのコンテンツサイトであり、表示速度、SEO、共有時の安定性が重要である。
そのため、可能な限り静的生成またはそれに近い配信方式を活かしつつ、投稿更新時に反映しやすい構成を採る。

### 3-2. コンテンツ構造を先に立てる

本サイトは単なるブログではなく、投稿を場所・季節・テーマなど複数軸で再利用する。
そのため、画面実装より先に、構造化されたコンテンツ管理を前提とする。

### 3-3. 写真は「原本」と「公開用」を分けて扱う

写真中心のサイトであるため、表示品質・パフォーマンス・安全性の観点から、原本管理と公開画像配信を分離して考える。
特に、EXIF/GPS情報やサイズ最適化の観点から、公開時に適した変換経路を持つことを前提とする。

### 3-4. AIは前処理と編集補助に限定する

AIは、文章生成や分類補助に使うが、公開ロジックや事実判断の主体にはしない。
また、位置情報や日時など、機械的に取得可能な情報はAIの前段で処理する。

### 3-5. MVPでは複雑な自動化よりも、明快な運用可能性を優先する

将来的に高度な自動化や外部データ連携はありうるが、MVPではまず「投稿できる」「探せる」「安全に公開できる」を安定して回すことを優先する。

### 3-6. 多言語対応は“最初から全部やる”のではなく、“後から足せる構造”を優先する

MVPでは日本語中心の運用を前提とし、全投稿の完全多言語化は目標にしない。
一方で、固定文言、固定ページ、メタデータ、ルーティング、CMSフィールド設計については、将来的な限定的英語対応を追加しやすい構造を意識する。

⸻

## 4. 想定アーキテクチャ概要

MVP時点では、以下のようなレイヤ構成を想定する。

1. フロントエンド / Webアプリケーション層
    公開サイト、投稿管理UI、メタデータ出力、SEO対応、将来的な固定文言のロケール切替余地を担う
2. コンテンツ管理層
    投稿、場所、分類語彙、関連リンク等を構造化して保持する
3. メディア管理層
    写真アップロード、公開用変換、配信最適化を担う
4. 地図・位置情報層
    地図表示、位置情報の保持、逆ジオコーディング補助等を担う
5. AI連携層
    タイトル・説明文・要約・分類候補の生成補助、必要に応じた翻訳ドラフト補助を担う
6. ホスティング / 配信層
    サイト配信、キャッシュ、デプロイ、環境管理を担う
7. 運用 / 安全管理層
    表記方針、写真公開ポリシー、AI利用方針に基づく確認・運用を担う

⸻

| フロントエンド基盤 | Next.js（App Router） | 0001 |
| ホスティング | Cloudflare（Workers/Pages）＋ R2 | 0001 |

### 5-1. フロントエンド / アプリケーション基盤

想定方針

* React系フレームワークを採用する
* SEO、OGP、構造化データ、動的メタ情報管理に対応しやすいことを重視する
* 静的生成またはそれに近い配信を活かしやすい構成を採る
* 投稿詳細、一覧、テーマ別、季節別、地図導線などを柔軟に構築できることを重視する
* 将来的な固定文言のロケール分離や限定的な英語ページ追加に対応しやすいことを重視する

確定（ADR-0001）

**Next.js（App Router）** を採用。公開側（SSG/ISR・SEO）と認証付き管理側（投稿編集・公開前チェックUI）とサーバ処理（EXIF除去・AI補助・公開ゲート）を単一スタックで完結でき、個人運営の運用負荷が最も軽い。比較（Astro / Remix）と採用理由の詳細は ADR-0001。

⸻

### 5-2. UI実装方針

想定方針

* レイアウトや余白の微調整をしやすいこと
* 写真主役の静かなデザインを実装しやすいこと
* モバイルファースト設計に向いていること
* フィルタ、ドロワー、ダイアログなどの基本コンポーネントを効率よく組めること
* 固定文言を将来的にロケール辞書へ切り出しやすいこと

現時点の前提

* Tailwind CSS
* 必要箇所に shadcn
* 本文フォント: Noto Sans JP
* 見出しフォント: Zen Kaku Gothic New

方針

これは現時点で維持する。
MVPでは、デザインシステムを大規模に独自構築するよりも、Tailwindベースで余白・タイポグラフィ・カード構造を細かく制御する方針が適している。

⸻

### 5-3. コンテンツ管理方式

想定方針

本サイトでは、投稿・場所・分類語彙・関連リンクなどを、単なる記事本文ではなく、構造化されたデータとして扱う。

確定（ADR-0002）

**フルカスタム（Drizzle ORM ＋ Cloudflare D1 ＋ R2、管理UIは自作）** を採用。
本プロダクトの核は、画像ごとの SafetyReview・PublishChecklist 公開ゲート・EXIF除去・AI補助といった**独自の編集/公開フロー**であり、汎用CMS（Markdown/Git・Headless SaaS・Payload等）に合わせるより、`12_data_model.md` の仕様をそのままスキーマ・管理UIへ落とす方が結局シンプル。`0001` の Cloudflare 単一スタックに収まり、低トラフィックなら無料枠内でほぼ¥0（超過は従量）・ベンダーロックなし。唯一の弱点は管理UIの自作工数。

* 比較（ファイルベース / Headless SaaS / Payload組み込み / フルカスタム）と見送り理由は ADR-0002。
* データモデルは `12_data_model.md`（エンティティを Drizzle スキーマ化）。

⸻

### 5-4. データモデルの大枠

MVP時点でも、最低限以下の概念を分けて持てる構造が望ましい。

* Post（投稿）
* Place（場所）
* Theme / Season / Tag（分類）
* Media（画像等）
* Link（関連リンク）
* StaticPage（固定ページ）またはそれに準ずる構造

基本方針

* Post と Place は分離を前提に考える
* 同じ場所に複数投稿が紐づけられる構造が望ましい
* 季節・テーマはタグと別役割で持つ
* 軽量投稿と通常投稿を同一の投稿エンティティ上で管理できるようにする
* 固定ページや一部メタ情報は、将来的に言語別フィールドを持てる余地を残す

詳細はデータ設計書で定義する。

⸻

### 5-5. 画像管理 / 配信

想定方針

写真は本プロダクトの中心要素であるため、以下を満たす必要がある。

* 表示速度が良い
* モバイルでも実用的
* サムネイルやサイズ変換が可能
* 公開用画像から不要なメタデータを落としやすい
* 原本と公開用を分けて扱える

確定（ADR-0003）

**R2 の二層構成（非公開 originals ＋ 公開 derivatives）＋ Cloudflare Image Transformations ＋ 自動検査** を採用。

* 原本（GPS入り）は R2 非公開に隔離し、配信経路に載せない。
* 公開は再エンコード済みの派生のみ。再エンコードで**EXIF/GPS をメタデータごと構造的に除去**（`08 §11-4`）。
* 公開派生に GPS が残っていないことを自動検査（配信前フック＋定期 Cron の二重）でアサートし、`SafetyReview.exif_gps_ok` を立てる。
* R2 の egress無料で低コスト。OGP/サムネは `ogp_ok=true` の派生を使う。
* 比較（Cloudflare Images / sharp 等）と詳細は ADR-0003。

⸻

### 5-6. 地図 / 位置情報基盤

想定方針

本サイトでは、地図は主要導線のひとつである。
ただし、MVPでは高度なGIS機能ではなく、場所から投稿へ辿れること が主目的となる。

確定（ADR-0004）

**MapLibre GL JS ＋ Protomaps（PMTiles）を R2 に自己ホスト** を採用。
ピン描画を自前で行うため、公開レベル A〜D の表示制御（代表地点・ぼかし・ピンなし・非表示）を完全に自分で実装できる。PMTiles を R2 に置けば API キー不要・egress無料（低トラフィックなら無料枠内でほぼ¥0）、ベンダーロックなし。比較（Google Maps / Mapbox / Leaflet）は ADR-0004。

MVPに必要なこと

* 投稿地点を地図上で表示できる（ピンは Place 単位、代表地点）
* 投稿数が少なくても破綻しない
* 公開レベルに応じて詳細地点を出しすぎない（C/D・map_display=false は地図データに含めない）
* 地図導線がスマホで扱いやすい

位置情報の扱い

* 画像EXIF由来のGPS情報と、公開用の地図表示位置は分けて考える
* 必要に応じて精度を落として表示できるようにする
* 逆ジオコーディング等はAIの前段で処理可能なものとして検討する
* Place に位置情報公開レベルを持たせる拡張余地を意識する

⸻

### 5-7. AI連携

想定方針

AIは、編集補助用途に限定する。
用途は以下を想定する。

* タイトル案生成
* 説明文ドラフト生成
* 要約生成
* テーマ / タグ候補生成
* 関連情報候補生成
* 必要箇所に限った翻訳ドラフト生成

技術方針

* 画像・メモ・取得済みメタ情報を入力に使う
* AIの前段で取得可能な情報は先に抽出する
* AI出力は保存可能だが、自動公開しない
* 出力結果は人が確認・編集できることを前提とする

確定（ADR-0005）

外部APIは **Anthropic Claude API** を採用。既定モデルは **Claude Haiku 4.5**（エイリアス `claude-haiku-4-5`＝正式ID `claude-haiku-4-5-20251001`）、編集品質を重視する生成のみ **Claude Opus 4.8**（`claude-opus-4-8`、Opus 系の最上位）。最上位の Claude Fable 5 は本用途に対し過剰なため採らない。低volumeで月額はごく小さい。比較（OpenAI / Gemini / Workers AI）は ADR-0005。

* 呼び出しはサーバ側（Route Handler / Server Action）。APIキーはサーバのみ。
* AIへ渡す画像は EXIF/GPS除去済みの派生（`0003`、`08 §11-4`）。GPS入り原本は送らない。
* 使用履歴は AIUsage（used / targets / human_review_level）として D1 に保存（`12 §4-9`）。

追加前提

* AI出力の表示ルール、責任境界、公開方針は 09_risk_ai_policy.md と整合させる
* 翻訳ドラフトは固定ページや必要箇所に限定し、全投稿への自動適用は前提としない

⸻

### 5-8. ホスティング / 配信基盤

想定方針

* モバイルでも安定して速い
* 個人運営でもデプロイ・運用しやすい
* SEOやキャッシュ制御に不利でない
* 開発フローと相性が良い

確定（ADR-0001）

**Cloudflare（Workers/Pages）＋ R2** を採用。egress無料が写真サイトに効き、月額をほぼ¥0〜低額に抑えられる。Vercel 固有の従量課金（画像最適化・転送量）に依存しない構成でコストを統制する。D1（DB）・R2（画像/PMTiles）・Workers（サーバ処理）と一体運用できる。詳細・コスト評価は ADR-0001。

⸻

### 5-9. 認証 / 管理UI

想定方針

初期は個人運営前提のため、閲覧者向け認証は不要とする。
必要なのは投稿・編集・公開管理のための管理UIであり、ADR-0002 で**自作の専用管理UI**（Next.js ＋ shadcn/ui）を採用済み。認証は管理者のみの限定ログインとする。画面仕様は `14_information_architecture.md §3-2 / §9`。

MVPで必要なこと

* 投稿作成 / 編集 / 公開切替
* 画像アップロード
* 分類付与
* AI補助結果の確認
* 公開前確認
* 固定ページ編集
* 将来的な英語固定ページ追加を阻害しないこと

将来の拡張

* 招待制投稿
* 役割別権限
* 承認フロー

などは後続フェーズで検討する。

⸻

## 6. 技術的に考慮すべき横断論点

### 6-1. SEO / メタデータ

MVPでも、以下は技術的に成立させる必要がある。

* title / description のページ単位設定
* OGP
* sitemap.xml
* robots.txt
* 構造化データ
* 固有URL
* 共有時の安定したメタ情報

この詳細は 07_seo_metadata_policy.md で定義する。

⸻

### 6-2. 非公式性の表示

個人運営サイトであることを適切に表示するため、以下を技術的に扱える必要がある。

* Aboutページ
* フッター表記
* OGP説明文
* サイト説明文
* プロフィール導線

この詳細は 05_public_private_policy.md で定義する。

⸻

### 6-3. 写真公開の安全性

画像アップロードから公開までの間に、少なくとも以下を扱える必要がある。

* EXIF / GPS の扱い
* 公開用画像生成
* 必要な確認フロー
* 人物や私有情報の公開判断支援

この詳細は 08_photo_location_policy.md で定義する。

⸻

### 6-4. コンテンツ可搬性

本サイトは「資産として残す」ことを重視するため、CMSや特定プラットフォームに過度に閉じないことが望ましい。
MVP時点では完全な仕組みを作り込まなくてもよいが、将来的にエクスポートやバックアップを取りやすい構造を意識する。

⸻

### 6-5. 限定的i18n対応余地

MVPでは全投稿の完全多言語対応は前提としないが、少なくとも以下を技術的に阻害しないことが望ましい。

* 固定文言をロケール別に切り出せること
* 固定ページに英語版を追加しやすいこと
* 必要に応じて /en/... のような限定的ロケールルーティングへ拡張可能であること
* メタデータやCMS項目が将来的な英語フィールド追加を妨げないこと

⸻

## 7. 現時点で確定しないもの

主要技術（フレームワーク / CMS / 画像配信 / 地図 / AI / i18n・slug）は **技術選定メモ（`15_adr/` 0001〜0006）で採用確定済み**。§5 の要約表を参照。

残る未確定は、実装詳細と MVP スコープの取捨に絞られる。

* 逆ジオコーディングや自動分類補助の具体方式（実装詳細）
* 原本（R2非公開 originals）の保持期間・削除方針（`0003` は隔離を確定。期間は運用で決める）
* EXIF自動検査の配置（CI / 配信前フック / 定期Cron）の具体実装（`0003`）
* Place 名寄せ（表記ゆれ統合）の運用ルール（`11_content_operations.md` で詰める）
* オフライン下書き対応の要否（MVPスコープ判断）
* RSS / Atom を MVP に含めるか（スコープ判断）
* hreflang 等の多言語SEO対応の時期（英語固定ページ導入時。`0006`）

これらは実装・運用フェーズ（Step 10 以降）で確定する。技術選定そのものの記録は `15_adr/`。

⸻

## 9. MVP実装の着手順序

技術選定は `15_adr/`（0001〜0006）で確定済み（2026-06-28）。ここからは Step 10（MVP実装）として、確定スタック上で以下の順に着手する。土台（プロジェクト → DB → 画像）を先に据え、その上に管理UI（＝安全ゲートの実装本体）、最後に公開側と配信を載せる。

1. **初期スキャフォールド**: Next.js（App Router）プロジェクト作成、Tailwind ＋ shadcn/ui、Cloudflare（Workers/Pages）＋ Wrangler、環境変数/secrets、リポジトリ整備（ADR-0001）。
2. **データ層**: Drizzle ORM で `12_data_model.md` のエンティティ（Post / Place / Season / Theme / Tag / Media / Link / StaticPage ＋ SafetyReview / PublishChecklist / AIUsage）を Cloudflare D1 のスキーマ化。Season/Theme の slug は `0006` の確定値（ADR-0002）。
3. **画像パイプライン**: R2 二層（非公開 originals / 公開 derivatives）、アップロード→EXIF読取→派生再エンコード（EXIF除去）→自動検査で `exif_gps_ok`（ADR-0003、`08 §11-4`）。
4. **管理UI ＋ 公開ゲート**: 投稿編集・Place管理・公開前チェックUI。SafetyReview（画像単位）/ PublishChecklist（投稿単位）を実装し、全項目充足まで公開不可（`14 §3-2 / §9`、`12 §5`）。管理者限定ログイン。
5. **AI補助**: Claude API をサーバ側で呼び、タイトル・要約・タグ・カテゴリ案を提示（人が確定）。AIUsage を記録（ADR-0005、`12 §4-9`）。
6. **公開側**: トップ・投稿詳細・Place詳細・テーマ/季節一覧・投稿一覧を SSG/ISR で構築（`14 §5`）。SEO・OGP・構造化データ・sitemap、slug、noindex/空ページ制御（`07`、`0006`）。
7. **地図**: MapLibre ＋ PMTiles(on R2)。公開レベル A〜D の表示制御、C/D・map_display=false は地図データに含めない（ADR-0004、`14 §5-6`）。
8. **配信・運用**: Cloudflare へのデプロイ、EXIF自動検査の配置（CI/配信前フック/定期Cron）、仮投稿データ（`trial-posts/`）の移行と画像再ホスト。

段階リリースの目安: 1〜4 で「安全に投稿・公開できる」最小系、5〜7 で「探して読める」公開体験、8 で運用固め。
