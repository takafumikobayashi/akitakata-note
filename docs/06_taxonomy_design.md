# 分類語彙設計メモ（改訂版）

## 1. 文書の目的

本書は、「あきたかたノート」における投稿分類の考え方を整理し、季節・テーマ・タグ・場所に関わる役割分担、初期語彙案、運用ルール、検証方法を定めるものである。

本サイトは、投稿を単に時系列で流すのではなく、場所・季節・テーマなど複数の文脈から再発見できる構造を重視している。
そのため、分類語彙は単なるラベルではなく、探索体験を支えるインデックス設計 として扱う必要がある。

また、本サイトでは写真・位置情報・人物写り込み・安全配慮が重要であるため、分類語彙の設計も、単に「見つけやすさ」だけでなく、安全に公開・整理できること を前提に考える。

本書の目的は以下の通りである。

* 季節・テーマ・タグの役割を明確に分ける
* 投稿時の迷いを減らし、継続しやすい分類運用を実現する
* 情報設計書・データ設計書・コンテンツ運用設計の前提を揃える
* 初期仮投稿を通じて語彙を調整するための土台を作る
* 写真・位置情報公開ポリシーと矛盾しない分類設計を行う

⸻

## 2. 基本方針

### 2-1. 分類は探索を助けるためにある

本サイトの分類は、コンテンツを厳密に学術分類するためではなく、外から来た人が地域を探索しやすくするため にある。
分類語彙は、運営者にとって付けやすく、閲覧者にとって意味が取りやすい粒度で設計する。

### 2-2. 最初から増やしすぎない

初期段階で分類を細かくしすぎると、投稿時の負荷が高くなり、導線も複雑になる。
そのため、MVPでは 少数のクローズド語彙 を基本とし、必要に応じてタグで補助する。

### 2-3. 「季節」「テーマ」「タグ」は役割を分ける

分類語彙は一括りにせず、少なくとも以下の3層で考える。

* 季節: 時期や季節感を表す語彙
* テーマ: 投稿がどの文脈で見られるべきかを表す語彙
* タグ: より自由度の高い補助情報

この役割を分けることで、導線・UI・運用を整理しやすくする。

### 2-4. 場所は分類の基点として別に扱う

場所は、季節やテーマと同列のラベルではなく、地図導線と地域理解の基点になる独立概念 として扱う。
そのため、Post に場所文字列を持つだけでなく、Place を独立した単位として設計する前提を持つ。

### 2-5. 分類設計は安全方針と矛盾しないことを優先する

探索性を高めるための分類であっても、写真・位置情報公開ポリシーやリスク・AI方針と矛盾してはならない。
特に、子ども、生活導線、私有情報、少人数活動などに関わる分類は、見つけやすさより安全性を優先 する。

### 2-6. 机上で固定しすぎず、仮投稿で検証する

初期語彙は文書上で仮置きするが、最終的には 初期10〜20本程度の仮投稿 を通じて、詰まり・重複・不足を確認しながら調整する。
分類語彙は、最初から完成版を目指すのではなく、実際の投稿内容に耐えるかどうか を見ながら固める。

⸻

## 3. 分類体系の全体像

本サイトでは、投稿に対して少なくとも以下の分類要素を持たせることを想定する。

* 場所（Place）
    地図導線と地域理解の基点となる
* 季節
    時期の表情や同じ場所の違いを示す
* テーマ
    関心や文脈ごとの探索導線を作る
* タグ
    個別の特徴や補助情報を示す

このうち、本書で主に扱うのは 季節・テーマ・タグ である。
ただし、場所の持ち方は分類設計と強く関係するため、最低限の方針をここでも扱う。

⸻

## 4. Place（場所）に関する前提

### 4-1. Placeの役割

Place は、単なる住所文字列ではなく、同じ場所に複数の投稿を紐づけるための単位である。
これにより、同じ場所の異なる時期、異なるテーマの投稿を結びつけやすくする。

### 4-2. PostとPlaceは分離前提とする

MVPでも、可能な限り Post と Place は分離する前提 で設計する。
投稿ごとに場所をベタ書きするだけでは、再発見性・地図導線・位置情報管理が不安定になりやすい。

### 4-3. Placeに持たせたい情報

Place には、将来的に以下のような情報を持たせることが望ましい。

* 場所名
* 表示用名称
* 緯度経度または代表地点
* 地図表示可否
* 位置情報公開レベル
* 補足説明

### 4-4. 位置情報公開レベルはPlace側で持つ前提を採る

写真・位置情報公開ポリシーとの整合を考えると、位置情報公開レベルは投稿ごとに毎回ゼロから判断するだけでなく、Place 側に基本レベルを持たせる前提 が望ましい。

想定するレベル例

* レベルA: 正確な代表地点を出してよい
* レベルB: おおよその地域表示に留める
* レベルC: 地名や地区名のみ
* レベルD: 地図非表示 / 非公開

ただし、最終的な公開判断は Post ごとの文脈も踏まえて行う。

⸻

## 5. 季節語彙の設計

### 5-1. 季節語彙の役割

季節語彙は、投稿が いつの空気感を持つか を表すためのものとする。
目的は、厳密な時候分類ではなく、閲覧者が「その時期らしさ」を感じながら辿れることにある。

季節語彙で担いたいこと

* 春夏秋冬の入口を作る
* 同じ場所の異なる表情を比較できるようにする
* 季節ごとの特集導線に繋げる
* 撮影時期の理解を助ける

### 5-2. 初期方針

MVPでは、季節語彙は シンプルなクローズド語彙 とし、まずは 四季ベース を採用する。

初期候補

* 春
* 夏
* 秋
* 冬

補助候補（必要に応じて）

* 通年

「見ごろ」「イベント期」などは季節そのものではなく、タグや補助情報で扱う方が望ましい。

### 5-3. 現時点で採らないもの

MVPでは、以下は採用しない方針とする。

* 二十四節気ベースの分類
* 月別を正式な主導線にすること
* 地域行事ごとに季節体系を細かく分けること

理由は、初期運用負荷が高く、分類の一貫性が保ちにくいためである。

### 5-4. 実務上の考え方

季節は、撮影月から機械的に仮判定し、人が必要に応じて調整する 方針が望ましい。
たとえば、撮影日から春夏秋冬を仮設定し、公開前に人が確認する。

⸻

## 6. テーマ語彙の設計

### 6-1. テーマ語彙の役割

テーマ語彙は、その投稿を どんな関心の文脈で見てもらうか を表す。
季節が「いつ」なら、テーマは「何として見るか」に近い。

テーマ語彙は、本サイトにおいて 探索導線の中心のひとつ になる。
したがって、テーマはタグよりも意味が明確で、一定の統制が取れた語彙である必要がある。

### 6-2. 初期方針

MVPでは、テーマは 運営者が管理するクローズド語彙 とする。
自由入力タグのように無制限に増やさず、初期導線として意味の通る少数のテーマに限定する。

### 6-3. 初期テーマ案

初期候補として、以下を仮置きする。

* 自然
    山、川、空、季節の風景、自然景観など
* 文化
    神楽、歴史、地域文化、祭り、行事など
* 日常
    まちなみ、暮らしの景色、何気ない風景など
* イベント
    期間限定行事、催し、にぎわいのある場面など
* 食
    飲食、食にまつわる風景、地域の食体験など
* 移動 / 行き方
    道のり、アクセス感覚、移動中の風景など

### 6-4. 補助候補

仮投稿の結果によっては、以下の追加を検討する。

* まちなみ
* 暮らし
* 風景
* 学び / 発見
* 散策

ただし、これらは意味が重なりやすいため、初期から増やしすぎない。

### 6-5. 初期テーマとして採らないもの

以下は、初期テーマとしては採らない方針を基本とする。

* 子連れ
* 子ども向け
* 生活圏を強く示唆するテーマ
* 少人数の活動主体を特定しやすいテーマ

理由は、写真・位置情報公開ポリシーにおいて、子どもの写り込みや生活導線の扱いが慎重であるためである。
これらは、探索導線として前面に出すよりも、必要性を慎重に見極めるべき領域と考える。

### 6-6. テーマ設計の原則

* テーマ数は少数に抑える
* 一般ユーザーに意味が通る語を使う
* 抽象度は揃える
* 1投稿に複数テーマを許容しすぎない
* 初期は 1〜2個程度まで に抑えるのが望ましい

### 6-7. 仮投稿で確認したテーマ運用の実態

仮投稿20本では、初期テーマ案6種（自然 / 文化 / 日常 / イベント / 食 / 移動・行き方）で過不足なく分類でき、新規テーマの追加は不要だった。
一方で、複数テーマ付与が一定数発生した（例: 文化＋自然＝郡山城跡、イベント＋文化＝夜神楽、文化＋移動・行き方＝神楽門前湯治村）。
§6-6の「1〜2個程度」という上限はおおむね守れたが、2個付与は例外ではなく常用される前提で、データ設計上テーマは複数選択可とする（§10-2の論点に対する回答）。

⸻

## 7. タグ設計

### 7-1. タグの役割

タグは、季節やテーマで表現しきれない 個別の特徴や補助情報 を示す。
テーマほど厳格に管理しないが、完全自由入力にすると散らかるため、初期は控えめに運用する。

タグで表したい例

* 夕景
* 桜
* 紅葉
* 川辺
* 神社
* 散歩
* 雨の日
* 朝
* 夜

### 7-2. 初期方針

MVPでは、タグは以下のように扱う。

* 完全自由入力にはしない
* 運営者が徐々に使う候補語を育てる
* AI候補生成は使うが、そのまま増殖させない
* タグは補助導線であり、主導線は季節・テーマ・場所とする

### 7-3. 慎重に扱うタグ

以下のようなタグは、初期運用では慎重に扱う。

* 子連れ向き
* 子ども向け
* 学校、保育、生活導線を想起させるもの
* 駐車場あり等の実用情報を断定するもの

理由は、写真安全方針・誤情報リスク・生活導線配慮と緊張しやすいためである。
必要な場合でも、タグより本文や補足情報で慎重に扱う方が望ましい。

### 7-4. テーマとタグの違い

例として、

* 自然 はテーマ
* 桜 はタグ
* 文化 はテーマ
* 神楽 はタグまたは将来のテーマ候補
* 日常 はテーマ
* 夕景 はタグ

というように、タグはより具体的・局所的な特徴を示す。

### 7-5. 仮投稿20本で確定したタグ統制語彙（初版）

trial-posts の仮投稿20本（2026-05時点）に実際にタグを当てた結果、以下の統制語彙が立ち上がった。
これを初期のクローズド候補とし、運用しながら育てる。

被写体・風景

* 桜 / 城跡 / 神社 / ダム湖 / 古建築 / 廃校 / 動物 / 朝もや / 夕景 / 展望 / まちなみ

食ジャンル

* お好み焼き / ラーメン / うどん / サンドイッチ / 道の駅グルメ

文化・歴史

* 神楽 / 夜神楽 / 毛利氏 / 歴史 / パワースポット / 花占い / アート / 祭り

場・施設

* 道の駅 / 温泉街 / 駅 / 産直

移動

* 芸備線

タグ数は1投稿あたり1〜3個に収まり、§7-1の「控えめ運用」と整合した。
テーマが具体名詞を吸えない部分（食→お好み焼き／ラーメン、文化→神楽／毛利氏）をタグが補完しており、テーマとタグの役割分離は機能している。

### 7-6. Place属性へ逃がすべきタグ

仮投稿で `温泉街` が4本（いずれも神楽門前湯治村）に出現した。
これは投稿ごとの特徴というより 場所そのものの属性 であり、Post のタグではなく Place 側の属性として持たせるべきである（§4-3 と整合）。
同様に、特定 Place に必ず付くタグは、Post タグとして毎回付与するのではなく Place 属性へ寄せる方針とする。

## 8. 分類の運用ルール

### 8-1. 投稿時に迷いすぎないことを優先する

分類設計は緻密であるより、投稿時に迷いすぎないこと を優先する。
1件の投稿に何分も悩むような分類設計は採らない。

### 8-2. 初期はクローズド語彙中心

MVPでは、季節とテーマはクローズド語彙を基本とする。
タグは補助的に扱い、増やしすぎない。

### 8-3. 未確定な場合は仮分類を許容する

分類に迷う投稿がある場合は、無理に厳密分類せず、仮分類または最小限の分類で公開できる余地を持たせる。
「分類できないから投稿できない」状態は避ける。

### 8-4. 再分類を前提にする

初期分類は確定版ではなく、仮投稿や運用を通じて見直す前提とする。
必要に応じて、過去投稿への再分類も行えるようにしておく。

### 8-5. 安全基準と衝突する場合は安全側を優先する

ある分類が探索導線としては魅力的でも、写真公開ポリシーやリスク方針と衝突する場合は、安全側を優先する。
分類は公開の正当化根拠にはならない。

⸻

## 9. 仮投稿による検証方針

### 9-1. 目的

机上の分類案が、実際の投稿内容に耐えられるかを確認する。
特に以下を検証する。

* テーマの粒度が揃っているか
* 季節語彙が十分か
* タグが多すぎないか
* どの分類で迷いやすいか
* 関連導線として使いやすいか
* 安全方針と衝突する分類がないか

### 9-2. 検証方法

初期の実写真・実メモを使って、10〜20本程度の仮投稿 を行う。
その中で、以下を記録する。

* 分類時に迷った箇所
* 似たテーマが重複した箇所
* タグで吸収したくなる内容
* 季節とテーマの役割が曖昧になった箇所
* 位置情報公開レベル判定で迷った箇所
* 子ども・生活導線・少人数活動との緊張があった箇所

### 9-3. 検証後に見直すこと

* テーマ数の増減
* テーマ名称の変更
* タグ候補の整理
* 季節の補助ラベルの扱い
* UIに出す分類の優先順位
* Place に持たせる位置情報公開レベルの運用粒度

### 9-4. 検証結果サマリ（仮投稿20本 / 2026-05実施）

trial-posts/ の Notion エクスポート20本（trial-001〜020）を対象に検証した結果は以下のとおり。

* 季節: 春 / 冬 / 通年 が出現。四季クローズド＋通年で不足なし（§5の方針を維持）
* テーマ: 初期6テーマで過不足なく分類でき、追加不要。複数付与が常用された（§6-7）
* タグ: §7-5の統制語彙が立ち上がった。1投稿1〜3個に収まり増殖は起きなかった
* Place: `温泉街` のように Place 属性へ寄せるべきタグを発見（§7-6）。Post / Place 分離の必要性が実データで裏づけられた
* 公開レベル（分類面）: A17／B2／C1。Bレベル（002,007）は座標を保持しつつ本文で地点をぼかす運用が機能した
* 安全方針との衝突: 分類（季節・テーマ・タグ）自体に安全方針との衝突はなかった。ただし別途実施した写真安全確認（`08_photo_location_policy.md`、2026-06）で、画像内容と公開レベルの不整合が見つかった。trial-002（Bだが画像内のランドマーク看板で交差点を特定可能）、trial-011（Cだが個人宅の居室窓・私有地が写り込み）。さらに画像36枚中35枚にGPSが残存。これらは分類ではなく画像・公開フロー側の課題であり、`08 §5-2 / §11`、`12_data_model.md §4-6 / §5-4` で対応済み
* 迷いの所在: テーマよりも「テーマとタグの境界」「特定 Place に紐づくタグの扱い」で判断が必要だった → §7-5・§7-6で整理済み

これにより、ロードマップ Step 5（仮投稿10〜20本）と Step 6（語彙設計の更新）の主要部分を満たした。
残課題は §10-2 のデータ設計論点（テーマ複数選択・タグの候補選択化・Place 位置情報公開レベル）であり、12_data_model.md（新規）へ引き継ぐ。

## 10. 情報設計・データ設計への影響

### 10-1. 情報設計への影響

* 地図・季節・テーマ導線のUIに直結する
* フィルタUIの数や粒度に影響する
* 関連投稿の見せ方に影響する
* 一覧ページやテーマページの設計に影響する
* Place 詳細ページや地図ピン導線の設計に影響する

### 10-2. データ設計への影響

* 季節を単一選択にするか
* テーマを単一 / 複数選択にするか
* タグを自由入力にするか候補選択にするか
* Place と Post の関係性にどう結びつけるか
* 未分類状態をどう保持するか
* Place に位置情報公開レベルを持たせるか
* 慎重テーマや慎重タグをどう管理するか

⸻

## 11. 現時点での暫定推奨

MVP時点では、以下を暫定推奨とする。

季節

* 春 / 夏 / 秋 / 冬 の4分類
* 撮影日時から仮設定可能
* 必要に応じて人が修正

テーマ

* 自然
* 文化
* 日常
* イベント
* 食
* 移動 / 行き方

タグ

* 補助情報として少数運用
* AI候補は参考にするが、無制限に増やさない
* 慎重タグは初期から増やしすぎない

Place

* Post と分離前提
* 同じ場所に複数投稿を紐づけられる構造を目指す
* 位置情報公開レベルを Place 側に持つ前提で検討する

運用原則

* テーマは初期はクローズド語彙
* 仮投稿10〜20本で見直す
* 投稿しやすさを優先する
* 将来の再分類を前提にする
* 安全基準と衝突する分類は採らない、または慎重に扱う

⸻

## 12. 今後の判断で参照すべき問い

* この分類は、閲覧者の探索を助けているか
* この語彙は、外部の人にも意味が通るか
* 投稿時に迷いすぎる設計になっていないか
* テーマとタグの役割が混ざっていないか
* 少ない投稿数でも導線として成立するか
* この分類は、安全方針や位置情報方針と矛盾していないか
* 将来の再分類や見直しに耐えられるか

⸻
