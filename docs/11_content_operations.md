# コンテンツ運用設計（改訂版）

## 1. 文書の目的

本書は、「あきたかたノート」のコンテンツ運用における基本方針、投稿フロー、公開条件、確認項目、AI活用方法、更新ルールを定めるものである。
本サイトは、現地で見たもの、感じたこと、撮影した風景を継続的に蓄積していく個人運営のローカルメディアであるため、1件ごとの完成度だけでなく、無理なく続けられる運用 が重要となる。

一方で、本サイトは写真・位置情報・人物写り込み・誤情報・非公式性・公私区分など、公開にあたって注意すべき論点が多い。
そのため、単に「投稿する」だけではなく、軽量に残すこと と 安全に公開すること を両立する運用フローが必要である。

本書の目的は以下の通りである。

* 撮影から公開、更新までの基本フローを定める
* 軽量投稿と通常投稿の運用ルールを定める
* AI補助の使い方と人の確認責任を明確にする
* 公開前チェックの実務ルールを整理する
* 日本語中心の運用を前提としつつ、限定的な英語対応の扱いを定める

⸻

## 2. 運用の基本方針

### 2-1. まず残し、あとで整える

本サイトでは、現地で得た断片を取りこぼさないことを重視する。
そのため、最初から毎回完成度の高い記事を書くことを前提にせず、写真1枚と短いメモからでも残せる運用 を基本とする。

### 2-2. 公開は軽く、判断は慎重に

投稿作業は軽く保つが、公開判断は慎重に行う。
特に、写真、位置情報、人物写り込み、私有情報、公式誤認、誤情報の可能性がある要素については、公開前に明示的な確認を行う。

### 2-3. AIは執筆者ではなく補助者

AIは下書き、要約、タグ候補、説明文候補、翻訳ドラフトの補助に使う。
ただし、公開責任は人が持つ。AI出力をそのまま公開する前提にはしない。

### 2-4. 日本語中心で継続可能性を守る

本サイトは日本語中心で運用する。
英語対応は、固定ページや必要性の高い情報に限定し、全投稿の完全多言語運用は前提としない。

### 2-5. 迷ったら出さない

公開の可否、写真の扱い、位置情報精度、翻訳の自然さ、公私区分などに迷いがある場合は、原則として 公開しない / 精度を落とす / 後回しにする を優先する。

⸻

## 3. コンテンツの種類

本サイトでは、運用上、コンテンツを以下のように扱う。

### 3-1. 軽量投稿

現地での記録を素早く残すための投稿。
主に以下で構成される。

* 写真1枚以上
* 場所情報
* 作成日時
* タイトルまたは短いメモ
* 最低限の分類情報

目的は、現地の断片を失わず残すことであり、後から整形する前提を含む。

### 3-2. 通常投稿

軽量投稿よりも文脈を補った投稿。
主に以下を持つ。

* 写真
* タイトル
* 説明文または本文
* 要約
* 場所
* 時期
* 季節 / テーマ
* 補足情報
* 関連リンク

目的は、写真と断片を、外部の人にも理解しやすい単位まで整えることである。

### 3-3. 固定ページ

投稿ではなく、サイト自体の理解を支えるページ。

* About
* このサイトについて
* 必要に応じた英語版固定ページ
* ポリシー関連ページ

### 3-4. 将来拡張コンテンツ

MVPでは中心ではないが、将来的に想定されるもの。

* 特集ページ
* 招待制投稿
* 地域の声の紹介
* 質問 / 回答コンテンツ

⸻

## 4. 運用フロー全体像

基本の流れは以下とする。

1. 撮影・記録
2. 下書き作成
3. 場所・時期・分類の補助入力
4. AI補助の利用（必要に応じて）
5. 公開前確認
6. 公開
7. 後編集 / 更新
8. 必要に応じて再分類・修正・非公開化

⸻

## 5. 投稿フロー

### 5-1. Step 1: 撮影・記録

現地で、写真と必要最小限のメモを残す。
この段階では完成度よりも、以下が重要である。

* その場でしか残せない景色を残す
* 後で思い出せる最低限のメモを残す
* 明らかに危うい写真はこの時点で候補から外す

メモの例

* どこで見たか
* 何が印象に残ったか
* 時間帯や天気
* 行き方で気づいたこと
* 季節感

### 5-2. Step 2: 下書き作成

CMSまたは管理UIにて、下書きを作る。
下書きの最低要件は以下とする。

* 写真1枚以上
* 場所情報
* 作成日時
* 短いメモは空欄でも可

この時点では公開前提でなくてよい。
重要なのは、後で整えられる状態で保存すること。

### 5-3. Step 3: 場所・時期・分類の補助入力

システムまたは人の判断で、以下を補う。

* 場所候補
* 時期
* 季節候補
* テーマ候補
* 位置情報公開レベル
* 地図掲載の可否

この段階では、分類は仮でもよい。
ただし、公開時には最低限の分類が必要となる。

### 5-4. Step 4: AI補助の利用

必要に応じて、以下をAIで補助生成する。

* タイトル候補
* 説明文ドラフト
* 要約
* description 候補
* テーマ / タグ候補
* 固定ページや必要箇所の翻訳ドラフト

AI利用は任意とする。
AIを使わない投稿があってもよい。

### 5-5. Step 5: 公開前確認

公開前には、技術処理済み項目 と 人確認項目 を確認する。
MVPでは高機能な承認ワークフローではなく、簡易チェックUIまたは確認画面 で以下の要点を確認できる状態を目指す。

最低限ここで確認する要点

* EXIF / GPS など機械処理済み項目に問題がないか
* 写真の人物写り込み、私有情報、位置情報精度に問題がないか
* 本文や補足情報が断定しすぎていないか
* 公式情報への導線が必要ではないか
* 公私の境界や非公式性の観点で問題がないか

### 5-6. Step 6: 公開

公開条件を満たしたもののみ公開する。

### 5-7. Step 7: 後編集 / 更新

公開後も、必要に応じて以下を行う。

* タイトル調整
* 説明文追加
* 分類修正
* 関連リンク追加
* 画像差し替え
* 訂正注記
* 非公開化

⸻

## 6. 軽量投稿と通常投稿の運用ルール

### 6-1. 軽量投稿の目的

軽量投稿は、現地の断片を失わず残すための正式な運用モード である。
「未完成な記事」ではなく、「軽い単位で成立する記録」として扱う。

### 6-2. 軽量投稿の公開最低要件

軽量投稿を公開するには、少なくとも以下を満たす。

* 写真1枚以上
* 場所情報
* タイトルまたは短いメモ
* title / description を生成可能であること
* 季節またはテーマのどちらか一方、もしくは仮分類を持つこと
* 公開前チェックを完了していること

### 6-3. 通常投稿の公開最低要件

通常投稿を公開するには、少なくとも以下を満たす。

* 写真1枚以上
* 場所情報
* タイトル
* 本文または説明文
* 季節またはテーマ
* title / description
* 公開前チェックを完了していること

### 6-4. 軽量投稿から通常投稿への更新

軽量投稿は、必要に応じて後から通常投稿相当に育ててよい。
更新の例は以下。

* タイトルを改善する
* 説明文を追加する
* 季節・テーマを精緻化する
* 関連リンクを追加する
* 行き方や背景説明を足す

⸻

## 7. 公開前チェック運用

### 7-1. 基本方針

公開前確認は、MVPでは高機能ワークフローではなく、簡易チェックUIまたは確認画面 により行う。
確認漏れを減らすことが目的であり、厳格な承認フローを作ることが目的ではない。

### 7-2. 技術処理済み項目

以下は、可能な限り技術で処理する。

* EXIF除去
* GPSの公開画像からの除去
* 公開用画像変換
* サムネイル生成

### 7-3. 人確認項目

公開前に少なくとも以下を確認する。

* 地図上の位置表示が適切か
* 顔が識別できる人物が写っていないか
* 子どもや少人数の参加者が特定されないか
* 表札、ナンバー、住宅入口などが写っていないか
* 私有地や生活導線の露出が過剰でないか
* OGP画像として不適切でないか
* 本文が断定しすぎていないか
* 公式情報への導線が必要ではないか
* 公私の境界に触れる内容ではないか

### 7-4. 迷う場合の対応優先順

1. 別画像に差し替える
2. トリミング・マスクする
3. 位置情報レベルを落とす
4. 地図導線から外す
5. 公開しない

⸻

## 8. AI活用の実務ルール

### 8-1. AIで補助してよいもの

* タイトル候補
* 説明文ドラフト
* 要約
* description
* タグ / テーマ候補
* 固定ページや必要箇所の翻訳ドラフト

### 8-2. AI出力の公開条件

AI補助テキストを公開するには、少なくとも以下を満たす。

* 人が全文確認している
* 不自然な断定表現がない
* 内容が写真や現地メモと整合している
* 必要に応じて公式情報への導線がある
* 翻訳の場合、意味の破綻や不自然な誤訳がない

### 8-3. AIを使わない方がよいケース

* 住民感情や地域文化の代表的説明
* 評価を含む記述
* 公私の境界が曖昧な話題
* 実用情報の断定
* 微妙なニュアンスが重要な翻訳

### 8-4. 内部的な記録

可能であれば、内部的に以下を保持する。

* AI補助あり / なし
* AI生成対象
* 人確認済みフラグ
* 最終更新日時

⸻

## 9. 英語対応・限定的i18n運用

### 9-1. 基本方針

本サイトは日本語中心で運用する。
英語対応は、固定ページや必要性の高い情報に限定して段階的に行う。

### 9-2. 初期に対象とする候補

* Aboutページ
* サイト説明
* 必要に応じた代表的な固定ページ
* 将来的に一部の代表投稿

初期に英語化する対象は、以下の条件に当てはまるものを優先する。

* サイトの性質や使い方を説明する固定情報である
* 翻訳しても意味の揺れが比較的小さい
* 英語化によって「公式案内」や「公的見解」に見えにくい
* 更新頻度が高すぎず、日本語版との整合を保ちやすい

逆に、以下は初期の英語化対象として慎重に扱う。

* 実用情報の変化が早いもの
* 公共交通、営業時間、制度情報など最新性が重要なもの
* 住民感情や地域文化のニュアンスが強いもの
* 行政や市政と誤認されやすい表現を含むもの

### 9-3. 英語対応の前提

* 全投稿の同時翻訳は前提にしない
* AI翻訳は補助に留める
* 公開責任は人が持つ
* 英語版がない投稿があってもよい

### 9-4. 英語対応の公開条件

英語版または英語説明を公開する場合は、少なくとも以下を確認する。

* 元の日本語の意図を大きく損なっていないか
* 不自然な機械翻訳になっていないか
* 公式案内のような強い断定になっていないか
* 実用情報が古くなっていないか
* 英語版だけ過剰に約束や断定をしていないか

### 9-5. 英語対応を見送る判断

以下の場合は、英語化しない判断を許容する。

* 翻訳の自然さに自信がない
* 更新同期が保てない
* 内容が一時的・局所的すぎる
* 誤解の方が大きいと判断される

⸻

## 10. 更新・修正・非公開化運用

### 10-1. 更新

以下のような更新を通常運用として許容する。

* 説明補足
* 分類修正
* タイトル調整
* 関連リンク追加
* OGP画像の見直し
* 英語版の追加 / 修正

### 10-2. 訂正

誤情報や誤解を招く表現が判明した場合は修正する。
必要に応じて、掲載時点情報であることや、更新した旨を示す。

### 10-3. 非公開化

以下の場合は非公開化を検討する。

* 個人情報露出
* 人物写真の不適切公開
* 公私衝突の疑い
* 誤訳が重大で修正前に公開継続が危険
* 地域への不利益が大きい

⸻

## 11. 運用上の役割分担

MVPでは個人運営を前提とするため、基本的には運営者本人が以下を担う。

* 撮影
* 下書き
* 分類補助確認
* AI補助利用判断
* 公開前確認
* 公開
* 更新 / 訂正 / 非公開判断

将来的に共同運用が発生する場合は、以下の分担が検討できる。

* 撮影担当
* 編集担当
* 公開確認担当
* 翻訳確認担当

ただし、MVPではまだ役割分離を前提にしない。

⸻

## 12. 定期的に見直すべき事項

運用開始後は、少なくとも以下を定期的に見直すことが望ましい。

* 軽量投稿の要件が重すぎないか
* 公開前チェックが現実的に回るか
* テーマ・季節語彙が破綻していないか
* title / description の生成運用が重すぎないか
* 英語対応が過剰になっていないか
* AI補助の使い方が責任境界を曖昧にしていないか
* 古い投稿の扱いに無理が出ていないか

⸻

## 13. MVPで最低限成立させるべき運用

MVPでは、少なくとも以下が成立していることを目標とする。

* 写真1枚と短いメモから下書きを作れる
* 軽量投稿として公開できる
* 公開前に安全確認ができる
* AI補助を使っても人の責任で公開できる
* 後から通常投稿相当に育てられる
* 個人運営・非公式性を保てる
* 英語対応は固定ページ等に限定し、無理なく回せる

⸻

## 14. 今後の判断で参照すべき問い

* この運用は、無理なく続けられるか
* 軽量投稿として成立しているか
* 公開判断は十分慎重か
* AI利用が責任を曖昧にしていないか
* 写真と位置情報の扱いは安全か
* この英語対応は本当に必要か
* 翻訳によって誤解を増やしていないか
* この更新は資産性と正確性のバランスを取れているか
