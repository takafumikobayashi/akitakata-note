# 10_進め方ロードマップ（改訂版）

## 1. 文書の目的

本書は、「あきたかたノート」を実装着手可能な状態まで進めるために、必要な文書整理、検証、意思決定、設計、実装準備の順序を整理するものである。
本プロジェクトは個人運営で進めるため、技術選定やドキュメント整備を過不足なく進めることが、継続性と実現可能性に直結する。

本書の目的は以下の通りである。

* 実装前に何をどの順で固めるかを明確にする
* 文書間の依存関係を整理する
* 仮投稿による検証フェーズを、設計工程の一部として位置づける
* 実装チームと認識を揃えやすくする
* 「考えすぎて止まる」ことと「決めないまま作り始める」ことの両方を避ける

⸻

## 2. 進め方の基本方針

### 2-1. まず思想と前提を整え、その後に実装へ進む

本プロジェクトは、一般的なブログや情報サイトではなく、探索性・資産性・写真中心・個人運営・非公式性・安全配慮など、複数の前提条件を持つ。
そのため、いきなり実装から入るのではなく、最低限必要な文書と判断基準を先に整える。

### 2-2. 机上設計だけで語彙や運用を固定しない

季節・テーマ語彙や投稿の軽量運用は、実際の投稿素材に触れないと固めにくい。
そのため、設計途中で 仮投稿による検証フェーズ を必ず挟む。

### 2-3. 技術選定は抽象論で終わらせず、ADRで順次確定する

技術設計概要は方向性を定める文書であり、最終的な採否判断は ADR に切り出す。
フレームワーク、CMS、画像配信、地図、AI API は、比較対象と採用理由を残しながら順次確定する。

### 2-4. MVPは「少なくても成立すること」を重視する

本プロジェクトでは、大量投稿や高頻度更新を前提にしない。
そのため、実装・設計・運用のすべてにおいて、少量投稿でも成立すること を判断基準にする。

### 2-5. 先に後戻りコストの高い実務論点を押さえる

ドメイン、表示名、非公式性、公開前チェック、投稿最低要件などは、後から変えると影響が大きい。
そのため、実装より先に、後戻りコストの高い論点を優先的に固める。

## 4. 全体フェーズ

本プロジェクトは、大きく以下のフェーズで進める。

Phase 0. 文書と判断基準を揃える

* 構想、設計思想、PRD、技術方針、表記方針、安全方針、運用方針を整理する
* 実装着手前に最低限必要な「ブレない軸」を作る

Phase 1. 仮投稿による設計検証

* 実際の写真・メモを使って仮投稿を行う
* 語彙、軽量投稿、地図導線、公開フローの詰まりを確認する

Phase 2. 設計確定と技術選定

* 仮投稿結果を反映して、情報設計・データ設計・運用設計を固める
* ADRで技術選定を確定する

Phase 3. MVP実装

* フロントエンド、CMS、画像、地図、AI補助、SEO基盤を実装する
* 公開前チェックと軽量投稿運用が成立する状態を目指す

Phase 4. 運用開始と初期改善

* 実際に投稿を始める
* 地図導線、語彙、公開フロー、閲覧体験を見ながら改善する

本プロジェクトでは、厳密な日付よりも 順序 が重要である。
推奨順は以下の通り。

1. 既存文書群を現状反映版に整える（完了）
2. 表示名・肩書き・ドメイン方針を確定する（完了）
3. ドメインを確保する（完了: akitaka-note.jp）
4. 仮投稿環境を決める
5. 仮投稿10〜20本を実施
6. 語彙設計を更新
7. データ設計書を作成
8. 情報設計書を作成
9. ADRで主要技術選定を確定
10. MVP実装着手

## 9. 今回のプロジェクトで避けるべき進め方

* 語彙設計や投稿運用を決めないままCMSを作り込む
* Place / Post 分離を曖昧なまま実装する
* 安全確認を「運用で頑張る」で済ませる
* SEO / OGP を後付け前提で後回しにする
* 高頻度更新を暗黙の前提にする
* 公私区分のルールを曖昧にしたまま公開を始める
* 表示名やドメインを後回しにしてブランド基盤を不安定にする
* 補強案をすべてMVP必須として重くしすぎる

⸻

## 10. 今後の判断で参照すべき問い

* 今この段階で決めるべきことか、仮投稿後でよいことか
* この判断は後戻りコストが高いか
* この仕様は少量投稿でも成立するか
* この運用は個人運営で継続できるか
* この設計は安全性と軽量性の両方を保てているか
* この順番で進めることで、実装チームが迷わず動けるか
