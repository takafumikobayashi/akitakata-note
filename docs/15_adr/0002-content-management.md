# ADR-0002 コンテンツ管理方式（CMS）

ステータス: **採用（Accepted）** — 2026-06-28 確定（フルカスタム: Next.js ＋ Drizzle ORM ＋ Cloudflare D1 ＋ R2、管理UI自作）

前提: `0001`（Next.js App Router ＋ Cloudflare/R2）採用済み。仮投稿は Notion 無料プランで実施したが、Notion を本番に転用するかは本ADRで判断する（`10` Step 4）。

## 背景・要件

本サイトのコンテンツ管理は、汎用ブログCMSにない**独自の編集・公開フロー**が中心になる（`08` `09` `12` `14`）。

* Post / Place の分離、Place 名寄せ・代表座標・基本公開レベル（`12 §4-2`、`06 §4`）。
* 画像ごとの **SafetyReview**（EXIF/GPS除去フラグ・AI顔検出提示・人物/表札/私有地/ランドマーク/OGP の項目別確認。`12 §4-10`、`14 §9-1`）。
* 投稿単位の **PublishChecklist 公開ゲート**（全項目充足まで status=公開にできない。`12 §5-1`、`14 §9-2`）。
* **EXIF/GPS除去**は構造で担保（原本隔離・派生のみ配信・自動検査。`08 §11-4`）。
* **AI補助**（タイトル・要約・タグ・カテゴリ案）と使用履歴（AIUsage。`09`、`12 §4-9`）。
* **スマホ投稿**前提（`03`）。低トラフィック・低更新頻度・個人運営。
* `0001` の Cloudflare/R2・低コスト前提を崩さないこと。

要点: これらの**ゲートとフック（EXIF・AI・公開可否）が要件の核**であり、「記事を書いて出す」だけの汎用CMSでは素直に表現できない。

## 候補

1. ファイルベース（MDX ＋ Git）
2. Headless SaaS（Sanity 等のホスト型）
3. コードファースト組み込み（Payload 3 を Next.js に統合 ＋ サーバDB）
4. フルカスタム（Drizzle ORM ＋ Cloudflare D1 ＋ R2、管理UIは自作）

## 比較観点

| 観点 | ファイルベース | Headless SaaS | Payload 組み込み | フルカスタム(D1) |
|---|---|---|---|---|
| 独自ゲート（SafetyReview/公開ゲート）適合 | ✕ | △（Studio拡張で無理筋寄り） | ◎（hook＋カスタム画面） | ◎（完全自由） |
| EXIF除去・AI補助のサーバフック | △ | △（外部前提） | ◎（lifecycle hooks） | ◎ |
| スマホ投稿 | ✕（ファイル編集が苦痛） | ◎ | ○（管理UI） | ○（自作UI） |
| Place/Post 分離・名寄せ | △ | ○ | ◎ | ◎ |
| Cloudflare/R2 適合（0001前提） | ◎ | ○ | △（Node＋外部Postgres寄り） | ◎（D1でフル Cloudflare） |
| コスト | ◎ ¥0 | ○（無料枠あり） | ○（Neon無料枠＋実行環境） | ◎ ほぼ¥0 |

| 構築工数 | ◎ 小 | ○ 中 | ◎ 小〜中（管理足場が無料） | △ 大（管理UI自作） |

## 決定

**フルカスタム（Next.js ＋ Drizzle ORM ＋ Cloudflare D1 ＋ R2、管理UIは自作）を採用する。**

採用理由

* 独自ゲート（SafetyReview / PublishChecklist）と EXIF/AI フックが**要件の核**であり、汎用CMSに合わせるより、`12`/`14` の仕様をそのままデータ・UIに落とす方が結局シンプル。
* `0001` の **Cloudflare/R2 前提を崩さず**、D1（SQLite）で完全に Cloudflare 内に収まる。低トラフィックなら D1/R2 の無料枠内でほぼ¥0（超過は従量）・ベンダーロックなし。
* 単一スタック（すべて Next.js）で公開・管理・サーバ処理を一貫管理できる。
* shadcn/ui で管理UI（投稿編集・公開前チェック・Place管理）を構築でき、`14 §9` の画面仕様が設計入力として既にある。

トレードオフ

* 管理UIを自作する**構築工数が最大**。ここが唯一の弱点。

## 見送り理由

* **ファイルベース（MDX/Git）**: スマホ投稿・画像ごとの構造化安全確認・AI使用履歴と相性が悪い。バイナリ画像を Git に置く運用も不適。本プロジェクトの編集フローに合わない。
* **Headless SaaS（Sanity 等）**: 無料枠は魅力だが、独自の公開ゲート・SafetyReview UI をホスト型 Studio に載せるのは無理筋寄りで、仕様変更・将来の価格・ベンダーロックの不確実性が個人運営の継続性に響く。
* **Payload 組み込み**: 管理足場・hook・アクセス制御が無料で手に入り**有力な次点**。ただし Node ランタイム＋外部 Postgres（Neon 等）を前提にしがちで、`0001` の Cloudflare/R2 前提から一歩外れる。→ 「管理UIの自作工数を最優先で削りたい」場合の代替として残す（§将来見直す条件）。

## 影響

* `0003 画像`: 原本隔離（R2 非公開）・派生再エンコード（EXIF除去）・自動検査の置き場所を、D1/R2/Workers 前提で具体化する。
* `0005 AI`: AIUsage の保存先は D1。AI呼び出しは Route Handler / Server Action。
* `12_data_model.md`: エンティティをそのままスキーマ化（Drizzle）。SafetyReview / PublishChecklist もテーブル化。
* `14_information_architecture.md §9`: 管理画面の実装対象が確定。

## 将来見直す条件

* 管理UI 自作の工数・保守が個人運営として過大と判明した場合 → **Payload 組み込み**へ切替（Node 実行環境＋ Postgres を許容）。
* D1 の制約（容量・機能・リージョン）が要件に合わなくなった場合 → Cloudflare 上の別DB（Hyperdrive 経由 Postgres 等）または managed Postgres へ。
* コンテンツ種別が増え、汎用CMSの編集体験が明確に有利になった場合。
