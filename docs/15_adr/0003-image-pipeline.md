# ADR-0003 画像管理 / 配信 / EXIF除去

ステータス: **採用（Accepted）** — 2026-06-28 確定（R2二層 ＋ Cloudflare Image Transformations ＋ 自動検査）

前提: `0001`（Next.js ＋ Cloudflare ＋ R2）、`0002`（フルカスタム ＋ D1 ＋ R2）採用済み。

## 背景・要件

画像は本プロダクトの中心要素であり、安全と低コストを両立する必要がある（`08` `12` `14`）。

* **EXIF/GPS除去を構造で担保**: 公開経路に原本を置かず、再エンコードした派生のみを配信する。除去は「最適化の副産物」とし独立工程に頼らない（`08 §11-4`）。
* **原本隔離**: 原本（GPS入り）は非公開ストレージへ。`Media.original_ref`（非公開）/ `public_url`（派生のみ）（`12 §4-6`）。
* **自動検査**: 公開領域の画像に GPS が残っていないことを継続的にアサートし、`SafetyReview.exif_gps_ok` を立てる（`12 §4-10`、`14 §9-1`）。
* **AI顔検出の提示**（確定は人。`08 §11-5`）の入力となる画像を扱える（具体APIは `0005`）。
* **スマホからのアップロード**、写真主役の高速表示（WebP/AVIF・レスポンシブ）。
* `0001` の Cloudflare/R2・**egress無料**を活かして低コスト（仮投稿の Notion 画像URLは1時間で失効するため本番は再ホスト必須。`12 §2-5`）。

## ストレージ構成（0001/0002 で確定済みの具体化）

* **R2: 非公開バケット/プレフィックス（originals）** — 原本。配信経路に出さない。
* **R2: 公開バケット/プレフィックス（derivatives）** — EXIF除去済みの派生のみ。Cloudflare CDN で配信（egress無料）。
* メタ（original_ref / public_url / order / alt / caption / safety_review）は D1（`12 §4-6`）。

## 候補（派生生成・EXIF除去エンジン）

1. **Cloudflare Image Transformations（Workers ＋ R2 連携）**: R2 の原本を URL/バインディングで変換し、フォーマット変換・リサイズ・メタデータ除去。派生を公開側にキャッシュ/格納。
2. **Cloudflare Images（マネージド製品）**: アップロード〜変換〜配信を一括。バリアント管理が楽。月額＋従量。
3. **sharp 等を Node 実行環境で**: 高機能だが Cloudflare Workers では native 不可（Node ランタイムが要る）。`0002` の Cloudflare 純度・コスト前提から外れる。

EXIF読み取り（除去の検証・撮影日/季節仮判定の材料）は、Worker 内の軽量 JS/WASM EXIF パーサで行う（仮検証で用いた純正パーサと同等の実装で代替可能。外部依存を増やさない）。

## 比較観点

| 観点 | Image Transformations(Workers+R2) | Cloudflare Images(managed) | sharp(Node) |
|---|---|---|---|
| EXIF/GPS除去（再エンコードで構造的に） | ◎ | ◎ | ◎ |
| Cloudflare/R2 適合（0001/0002前提） | ◎ | ◎ | △（Node必須） |
| コスト（egress無料・低額） | ◎ | ○（月額＋従量） | △ |
| 制御の自由度（命名・派生戦略） | ◎ | ○ | ◎ |
| 構築/運用の手間 | ○ | ◎（一括で楽） | △ |
| ベンダーロック | ○ | △ | ◎ |

## 決定（提案）

**Cloudflare Image Transformations（Workers ＋ R2）を第一候補とする。** 構成は以下。

1. スマホ等からアップロード → **原本を R2 非公開（originals）へ保存**（EXIF付きのまま隔離）。
2. アップロード時に **EXIF を読み取り**、撮影日（季節仮判定の材料、`06 §5-4`）や内部用途の情報を D1 に記録。**GPS は内部記録に留め、公開面・派生には一切持ち出さない**。
3. **派生生成**: Image Transformations で WebP/AVIF＋レスポンシブ各サイズに再エンコード。この再エンコードで**メタデータが構造的に除去**される。派生を公開（derivatives）として配信/キャッシュ。
4. **自動検査**: 公開派生に GPS/EXIF が無いことを検査し（配信前フック＋定期 Cron Worker の二重）、`SafetyReview.exif_gps_ok` を立てる。残存検出時は公開ゲートで停止（`12 §5-1`）。
5. **配信**: 公開派生のみを R2＋CDN で配信（egress無料）。OGP画像も `ogp_ok=true` の派生を使う（`07 §6-2`）。
6. AI顔検出（`0005`）には派生または原本（サーバ内処理のみ）を渡し、枠を提示。確定は人。

採用理由

* EXIF除去を**再エンコードの副産物**として構造化でき（`08 §11-4`）、原本隔離＋自動検査と合わせて「公開面に GPS が出ない」を仕組みで保証。
* R2 の **egress無料**と Transformations で、低トラフィックの写真サイトを**低コスト**運用できる。
* `0001/0002` の Cloudflare 単一スタックに収まり、外部依存・ロックを最小化。

## 見送り理由

* **Cloudflare Images（managed）**: 一括で楽だが月額＋従量が乗り、派生命名やバケット戦略の自由度が下がる。→ 自前の Transformations 運用が重いと判明したら切替候補（§見直し条件）。
* **sharp(Node)**: 高機能だが Cloudflare Workers で native 不可。Node 実行環境を別に用意すると `0002` の前提・コストから外れる。

## 影響

* `12 §4-6 / §4-10`: original_ref（非公開R2）/ public_url（派生）/ exif_gps_ok（自動検査結果）の運用が確定。
* `0005 AI`: 顔検出に渡す画像の出所（派生 or サーバ内原本）を定義。
* `08 §11-4`: 構造的除去＋自動検査の実装場所（Workers＋Cron）が具体化。
* 価格・無料枠（Transformations / R2）は確定時に要再確認。

## 将来見直す条件

* Transformations の自前運用（派生戦略・キャッシュ・検査）が個人運営として重いと判明 → Cloudflare Images（managed）へ。
* 画像点数・トラフィック増で R2／変換コストが過大化 → 配信戦略（事前生成 vs オンデマンド）を再設計。
* より高度な画像処理（顔ぼかしの自動適用等）が必要になり Workers で困難 → Node 処理層の追加を検討（コスト影響を再評価）。
