# ADR-0001 フロントエンド基盤

ステータス: **採用（Accepted）** — 2026-06-28 確定（Next.js App Router ＋ Cloudflare/R2 前提、コスト観点を加味）

## 背景・要件

「あきたかたノート」のフロントエンド基盤を決める。本ADRはフレームワークの選定に限定し、ホスティング（`0001` の影響先として別途確定）と CMS（`0002`）は分けて扱う。

満たすべき要件（`02` `03` `07` `08` `12` `14` より）

* 写真主役・高速表示・SEO（SSG/ISR、構造化データ、OGP、sitemap、noindex制御）。
* 公開側（探索・投稿詳細・Place・テーマ/季節・地図）と、認証付き管理側（投稿編集・公開前チェックUI）の両方を備える。
* サーバ処理が必要: 画像のEXIF/GPS除去・派生生成（`08 §11-4`）、AI補助呼び出し（`09`）、公開ゲート判定（`12 §5`）。
* 画像最適化が一級であること（写真が中心）。
* 地図ライブラリと親和（`0004`）。
* 将来の限定的 i18n 余地（`/en/...`、`07 §9-4`、`0006`）。
* UI: Tailwind CSS ＋ shadcn/ui、Noto Sans JP / Zen Kaku Gothic New（既定方針）。
* **個人運営**: 学習・運用・コストが軽いこと。単一スタックで完結できると望ましい。

## 候補

* Next.js（App Router, React）
* Astro（＋必要箇所のみ React/島）
* Remix（React）

## コスト評価

前提: フレームワーク本体（Next.js / Astro / Remix）はいずれも OSS で**ライセンス費用ゼロ**。実際の月額コストは主に **ホスティング** と **画像変換/配信** に出るため、フレームワーク選定は「どのホスティング/画像戦略を取りやすいか（＝コストの天井）」で評価する。仮投稿フェーズが ¥0（Notion 無料）だった文脈とも整合させ、**通常運用で月額をほぼ¥0〜低額に抑えられること**を重視する。

コスト構造（低トラフィックの写真サイト想定。価格は概算で、確定時に要再確認）

* **ホスティング**
  * Cloudflare（Pages / Workers）: 無料枠が広く、超過しても小規模。**egress（転送量）無料**が写真サイトに効く。→ 低コスト基調にしやすい。
  * Vercel: Hobby は無料だが商用は実質 Pro（月額課金）。画像最適化・転送量が従量で乗りうる。→ 便利だがコストが逓増しやすい。
* **画像変換/配信**（詳細は `0003`）
  * Cloudflare R2（無料枠あり。egress無料、ストレージ/操作は超過課金）＋ 変換、または Cloudflare Images（少額固定＋従量）。→ 低トラフィックなら低コスト。
  * Vercel の画像最適化は使用量に応じて課金されうる。→ コスト注意。
* **ビルド/関数実行**: 低頻度更新（個人運営）なら無料枠内に収まりやすい。

フレームワーク別のコスト含意

* **Next.js**: 既定の動線は Vercel で、そのままだとコストが逓増しやすい。ただし **Cloudflare（Workers/Pages）＋ R2 で運用すれば月額をほぼ¥0〜低額に抑えられる**。＝コストはホスティング選択でコントロール可能。
* **Astro**: 静的寄りで最も移植容易・最安。Cloudflare 無料枠でほぼ¥0運用がしやすい。ただし管理側（動的・認証・サーバ処理）を別立てにすると、その分の運用（時間）コストが乗る。
* **Remix**: Next.js と大枠同等。コスト上の明確な優位はない。

結論（コスト観点）: **フレームワーク自体はコスト差を生まない。** コストの主因はホスティングと画像戦略であり、**「Vercel 前提にしない」ことが最大のコスト統制レバー**。Next.js を選んでも Cloudflare＋R2 を前提にすれば、Astro と同水準の低コストを狙える。絶対的な最小コスト・最大移植性のみを最優先するなら Astro が一段有利。

## 決定

**Next.js（App Router）を採用する。ホスティングは Cloudflare（Workers/Pages）＋ R2 を既定の前提とし、Vercel 固有の従量課金（画像最適化・転送量）に依存しない構成でコストを抑える。**

採用理由

* 公開側（SSG/ISR・SEO・next/image）と、認証付き管理側（投稿編集・公開前チェックUI）と、サーバ処理（EXIF/GPS除去・派生生成・AI補助・公開ゲート判定）を**単一スタックで完結**でき、個人運営での運用面が最も軽い。
* 写真主役に効く画像最適化が一級。Tailwind ＋ shadcn/ui（React）と親和。
* Route Handlers / Server Actions で `12` の公開ゲート・`08` の画像パイプライン・`09` のAI補助呼び出しをサーバ側に集約しやすい。
* i18n・地図・ホスティングの選択肢が広く、後続ADR（0003〜0006）の自由度を狭めない。
* **コスト**: フレームワーク本体は無償。Cloudflare＋R2 を前提にすれば、単一スタックの運用簡素さを保ちつつ月額をほぼ¥0〜低額に抑えられる（コスト評価節）。Astro 並みの低コストを Vercel 非依存で実現できる。

## 見送り理由

* **Astro**: 公開コンテンツサイトとしては最良で高速、かつ最も移植容易で**最安**になりやすい。ただし認証付き管理UIとサーバ処理を別スタックに分けがちで、個人運営では「公開Astro＋管理別アプリ」の二重運用（時間コスト）が負担になりうる。金銭コストの優位は、Next.js を Cloudflare＋R2 で運用すればおおむね相殺できると判断。→ 「絶対的な最小コスト・最大移植性」または「管理側を完全に分離する」方針を採る場合は最有力の代替として残す（§将来見直す条件）。
* **Remix**: フルスタックとして妥当だが、画像最適化・エコシステム・shadcn等の周辺で Next.js に対する明確な優位が薄く、個人運営の情報入手性でも劣後。

## 影響

* `0002 CMS`: Next.js 前提で「ファイルベース / Headless / DB」を比較する。
* `0003 画像パイプライン`: Route Handlers／ビルド処理での EXIF除去・派生生成・自動検査の置き場所を決める。
* `0004 地図`: React 親和の地図ライブラリ（MapLibre 等）を前提化できる。
* `0006 i18n`: next-intl 等の App Router 対応方式を前提化できる。
* ホスティングは本ADRで **Cloudflare（Workers/Pages）＋ R2 を既定の前提**とする（コスト統制のため Vercel 従量課金に依存しない）。最終的な構成詳細は `0003`（画像）とあわせて確定する。

## 将来見直す条件

* 管理側を完全分離（公開は静的、管理は別SaaS/別アプリ）する方針に変える場合 → Astro が再浮上。
* ビルド時間・ホスティングコストが個人運営として過大になった場合（特に Cloudflare＋R2 前提が崩れ、Vercel 従量課金に依存せざるを得なくなった場合）。
* 月額コストの最小化が単一スタックの簡素さより優先されると判断した場合 → Astro＋Cloudflare（公開）＋管理分離 を再評価。
* Astro の Server Islands 等が成熟し、管理側まで無理なく賄えると判断できた場合。
* 採用フレームワークの長期保守性・破壊的変更頻度が運用継続性を損なうと判断した場合。
